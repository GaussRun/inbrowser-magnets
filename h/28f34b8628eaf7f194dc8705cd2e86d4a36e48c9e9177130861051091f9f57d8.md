# Field notes on every host the reader can use

This is the large test post for inbrowser-magnets. It is about one hundred
kilobytes, which is deliberately above what most Nostr relays accept in one
event and deliberately below the 107,520 byte free limit of the Arweave Turbo
service. It exists so the reader is tested with a post that some sources will
refuse and other sources will serve slowly. The text is real: it is the working
notes behind the choice of hosts, written out in full, one host at a time, with
the same questions asked of each.

The questions are always the same six:

1. What does it take to write there, and is it free without an account?
2. What URL serves the bytes back, and does it send CORS headers?
3. Does the host keep the bytes unchanged, so the hash still matches?
4. How long has it been there, and how long do its old blobs survive?
5. What rate limits or size limits apply?
6. What is the failure mode, and how would the reader notice?

Hosts are grouped by family. Inside a family the order is the order the reader
tries them. Nothing in this document is a recommendation to depend on any one
host; the recommendation is the opposite.

## GitHub family

A public repository on GitHub is served through four different front doors. One push updates all four, and they fail independently: raw.githubusercontent.com is GitHub's own, jsDelivr and Statically are third party CDNs that pull from GitHub, and GitHub Pages is a separate build and deploy pipeline. All four send `access-control-allow-origin: *` for files in a public repository, which is the only thing the reader needs from them.

### raw.githubusercontent.com

**Writing.** A git push to a public repository. No account beyond the GitHub account that owns the repository, which already exists.

**Reading.** https://raw.githubusercontent.com/GaussRun/inbrowser-magnets/main/h/<hex>.md with CORS *; content type is always text/plain.

**Byte exactness.** Byte exact. Git stores the blob and the raw endpoint streams it.

**Age and retention.** As old as GitHub. A repository deleted by its owner or by a takedown vanishes from all four front doors at once, which is the main correlated failure in this family.

**Limits.** Soft rate limit per IP that shows up as HTTP 429 during bursts; a single reader never sees it.

**Failure mode.** HTTP 404 for a missing path, 429 when throttled, connection error when blocked at the network level. All three are ordinary fetch failures.

### cdn.jsdelivr.net

**Writing.** Nothing. It pulls from GitHub on first request and caches at the edge.

**Reading.** https://cdn.jsdelivr.net/gh/GaussRun/inbrowser-magnets@main/h/<hex>.md with CORS *; content type guessed from the extension.

**Byte exactness.** Byte exact for files under the size limit; jsDelivr refuses files over 20 MB and that is far above any post.

**Age and retention.** Since 2012. It has survived several changes of sponsor and edge provider.

**Limits.** A branch reference is cached for about 12 hours, so a brand new file may 404 for a while and then appear; a commit hash reference is immutable.

**Failure mode.** 404 for a path that was not there when the cache was filled, or a stale copy for a path that changed; stale copies are harmless because the hash check rejects them.

### cdn.statically.io

**Writing.** Nothing. Same model as jsDelivr.

**Reading.** https://cdn.statically.io/gh/GaussRun/inbrowser-magnets/main/h/<hex>.md with CORS *.

**Byte exactness.** Byte exact for text; Statically offers image optimisation on a different path, which is never used here.

**Age and retention.** Since 2018, smaller operator than jsDelivr.

**Limits.** Long edge cache, about a year for a branch reference, which again is harmless because the file at a hash path never changes.

**Failure mode.** Same as jsDelivr. The two CDNs are listed because they are independent of each other and of GitHub Pages, even if they both depend on the repository existing.

### gaussrun.github.io

**Writing.** A GitHub Actions workflow that uploads the repository as a Pages artifact and deploys it. The owner has to enable Pages once in the repository settings.

**Reading.** https://gaussrun.github.io/inbrowser-magnets/h/<hex>.md; Pages sends CORS * and a content type derived from the extension.

**Byte exactness.** Byte exact; Pages serves the artifact as is when there is a .nojekyll file at the root.

**Age and retention.** Since 2008 as a feature. The reader uses it as the home host in the test links, so the test with a dead home host is exactly the test where this one is down.

**Limits.** Ten builds per hour, 1 GB site size, 100 GB bandwidth per month. Irrelevant at this scale.

**Failure mode.** A 404 page that is itself HTML. The reader must not render it; the integrity check makes sure it does not.

## Blossom family

Blossom is a tiny HTTP protocol from the Nostr world: PUT a blob to /upload with a signed authorisation event in the Authorization header, GET it back at /<sha256>. The server is required to store the exact bytes and to serve them with CORS headers. There is no account; the key that signs the authorisation is the only identity, and a fresh key works on the open servers. These are the seven servers the reader tries without a hint, in order.

### nostr.download

**Writing.** PUT /upload with a kind 24242 event, t=upload, x=<hex>, expiration about an hour ahead. Returns a descriptor with url, sha256, size and type.

**Reading.** https://nostr.download/<hex> with CORS *, 10 GB per file limit, mirror endpoint available.

**Byte exactness.** Byte exact; the descriptor sha256 is checked against ours after every upload.

**Age and retention.** Blobs from 400 days ago still served when probed. Best evidence among the general purpose servers.

**Limits.** None published. The publisher waits three seconds between uploads anyway.

**Failure mode.** 404 for an unknown hash, 401 for a bad authorisation, 413 for too large. Ordinary.

### blossom.ditto.pub

**Writing.** Same protocol. Accepts text and images from any key.

**Reading.** https://blossom.ditto.pub/<hex> with CORS * and cache-control: immutable.

**Byte exactness.** Byte exact; no /media endpoint, so there is no path by which it could re-encode anything.

**Age and retention.** Over a million blobs, old blobs still served after 400 days.

**Limits.** 2 GB per file.

**Failure mode.** Ordinary.

### cdn.hzrd149.com

**Writing.** Same protocol; run by the author of the specification, which makes it the reference behaviour.

**Reading.** https://cdn.hzrd149.com/<hex> with CORS *.

**Byte exactness.** Byte exact on /upload; its /media endpoint re-encodes images and is never used.

**Age and retention.** Since the specification exists; about 150 thousand blobs.

**Limits.** 2 GB per file.

**Failure mode.** Ordinary.

### blossom.yakihonne.com

**Writing.** Same protocol. Explicitly allows text/* in its upload policy.

**Reading.** https://blossom.yakihonne.com/<hex> with CORS *.

**Byte exactness.** Byte exact on /upload.

**Age and retention.** Blobs from 120 days served, one from 250 days gone, so retention is shorter than the first three.

**Limits.** 200 MB per file.

**Failure mode.** Ordinary; the mirror endpoint refuses, which only matters for fan-out.

### blossom.nmail.li

**Writing.** Same protocol.

**Reading.** https://blossom.nmail.li/<hex> with CORS *.

**Byte exactness.** Byte exact; /media disabled.

**Age and retention.** Unknown; no old blob was sampled.

**Limits.** Not stated.

**Failure mode.** Ordinary.

### blossom.jumble.social

**Writing.** Same protocol, but the upload preflight refuses text/markdown, so the publisher sends Markdown as text/plain. The bytes are the same; only the declared type differs.

**Reading.** https://blossom.jumble.social/<hex> with CORS *.

**Byte exactness.** Byte exact.

**Age and retention.** Blobs from 30 days served; longer not sampled.

**Limits.** 20 MB per file, 10 uploads per minute and 30 per hour per address. The publisher stays far below that.

**Failure mode.** 429 when the per-address limit is hit; the publisher backs off and retries on the next run.

### files.sovbit.host

**Writing.** Same protocol.

**Reading.** https://files.sovbit.host/<hex> with CORS *.

**Byte exactness.** Byte exact.

**Age and retention.** Unknown.

**Limits.** 10 MB per file, 500 MB per key.

**Failure mode.** Ordinary.

## IPFS family

IPFS names a file by the hash of its content. For a file under one mebibyte stored as one raw block, the name is a thin wrapper around sha256, so the reader can compute it from the hex in the link without any extra information. The bytes are pinned once, at Lighthouse, and a second time at Fula, and any public gateway that can find the providers will serve the raw block at /ipfs/<cid>?format=raw. The gateways below are the ones that still work after the large sponsored gateways were retired in September 2026.

### ipfs.filebase.io

**Writing.** Nothing; a gateway. The pin lives elsewhere.

**Reading.** https://ipfs.filebase.io/ipfs/<cid>?format=raw with CORS *, content type application/vnd.ipld.raw.

**Byte exactness.** Byte exact by construction; a gateway that served different bytes would be serving a different CID.

**Age and retention.** Filebase has operated since 2019 on its own edge.

**Limits.** None observed for reads.

**Failure mode.** 504 or a long hang when the providers for a fresh CID cannot be found. The reader aborts the request when another source wins.

### gateway.pinata.cloud

**Writing.** Nothing; a gateway.

**Reading.** https://gateway.pinata.cloud/ipfs/<cid>?format=raw with CORS *.

**Byte exactness.** Byte exact.

**Age and retention.** Since 2018.

**Limits.** Five to six seconds of latency on a cold CID was typical in probes.

**Failure mode.** Same as above, plus occasional 429 from the shared public gateway.

### ipfs.4everland.io

**Writing.** Nothing; a gateway.

**Reading.** https://ipfs.4everland.io/ipfs/<cid>?format=raw with CORS *, behind Cloudflare.

**Byte exactness.** Byte exact.

**Age and retention.** Since 2021.

**Limits.** A large file timed out once at 25 seconds in probes; posts are small.

**Failure mode.** Same as above.

### ipfs.blockfrost.dev

**Writing.** Nothing; a gateway.

**Reading.** https://ipfs.blockfrost.dev/ipfs/<cid>?format=raw with CORS *; the query string form is required because the Accept header form was cached once without the CORS header.

**Byte exactness.** Byte exact.

**Age and retention.** Since 2021, BunnyCDN edge.

**Limits.** None observed.

**Failure mode.** Same as above.

### ipfs.aleph.cloud

**Writing.** Nothing; a gateway.

**Reading.** https://ipfs.aleph.cloud/ipfs/<cid>?format=raw with CORS *.

**Byte exactness.** Byte exact.

**Age and retention.** Since 2020, independent infrastructure.

**Limits.** None observed.

**Failure mode.** Same as above.

### gateway.pinme.dev

**Writing.** Nothing; a gateway.

**Reading.** https://gateway.pinme.dev/ipfs/<cid>?format=raw with CORS *.

**Byte exactness.** Byte exact.

**Age and retention.** Newer than the others.

**Limits.** None observed.

**Failure mode.** Same as above.

### ipfs.cloud.fx.land

**Writing.** Fula pins by CID through the standard pinning service API: POST /pins with the CID and a name, then poll until the status is pinned.

**Reading.** https://ipfs.cloud.fx.land/ipfs/<cid>?format=raw; CORS is checked by the publisher after every run.

**Byte exactness.** Byte exact.

**Age and retention.** Newer service; included as a second, independent provider for the same block.

**Limits.** Not stated for the free tier.

**Failure mode.** A pin that stays queued; the publisher records the status verbatim.

## Arweave family

Arweave is a blockchain whose only job is to store data permanently, paid once. The Turbo bundler accepts items under 105 KiB for free and without a signature, and the item appears on every ar.io gateway at /raw/<txid> within minutes. Custom tags are indexed, so the reader can also find an item by a Content-SHA256 tag through GraphQL when the link has no transaction id. The free allowance is 10 MiB per address and per IP for life, which is about a hundred posts of this size or a thousand of the small size.

### arweave.net

**Writing.** Upload through Turbo. The transaction id is recorded in the manifest and placed in the link as an a: hint.

**Reading.** https://arweave.net/raw/<txid> with CORS *; /raw serves the bytes without manifest interpretation.

**Byte exactness.** Byte exact; the bytes are what was signed into the bundle.

**Age and retention.** Since 2018. The protocol endowment is designed to pay for storage for two hundred years.

**Limits.** None for reads.

**Failure mode.** 404 while the bundle is being indexed; the test run waits and retries.

### ar-io.dev

**Writing.** Nothing; a gateway.

**Reading.** https://ar-io.dev/raw/<txid> with CORS *.

**Byte exactness.** Byte exact.

**Age and retention.** The reference ar.io gateway.

**Limits.** None observed.

**Failure mode.** Same as above.

### turbo-gateway.com

**Writing.** Nothing; the bundler's own gateway, which serves an item optimistically before it is on chain.

**Reading.** https://turbo-gateway.com/raw/<txid> with CORS *.

**Byte exactness.** Byte exact.

**Age and retention.** Since Turbo exists.

**Limits.** None observed.

**Failure mode.** Should be the first to have a fresh item.

### ardrive.net

**Writing.** Nothing; a gateway.

**Reading.** https://ardrive.net/raw/<txid> with CORS *, GraphQL at /graphql.

**Byte exactness.** Byte exact.

**Age and retention.** Run by the ArDrive team.

**Limits.** A broad tag query hit a row limit once; exact sha256 filters are fine.

**Failure mode.** Same as above.

## Software Heritage

Software Heritage is a public archive of source code run as a non-profit under UNESCO patronage. Anybody can ask it to archive a public git repository, and once archived every file in the repository is served by its hash, including sha256, through a documented API with CORS headers. It is slow to ingest, hours sometimes, and it is rate limited for anonymous use, but it is the only host in this list whose stated mission is to keep the bytes forever.

### archive.softwareheritage.org

**Writing.** POST /api/1/origin/save/git/url/<repository url>/ with no authentication. The request is queued and a crawler clones the repository.

**Reading.** https://archive.softwareheritage.org/api/1/content/sha256:<hex>/raw/ with CORS *, content type application/octet-stream.

**Byte exactness.** Byte exact; it is addressed by hash.

**Age and retention.** Since 2016; funded as infrastructure, not as a product.

**Limits.** 120 anonymous API requests per hour, which is why it sits late in the reader's order and why the publisher polls slowly.

**Failure mode.** 404 until the first visit of the repository completes; 429 when the anonymous quota is spent.

## Nostr relays

A relay is a WebSocket server that stores signed events and answers filters. A kind 30023 event is a long-form article; the publisher adds an x tag with the sha256 of the Markdown so a relay can answer a #x filter with the article. The content of the event must be the exact Markdown bytes, so the reader can hash it. Most relays run strfry with a 64 KiB event limit, so this post does not fit on them, and the publisher records which relays refused it. The ten below are tried in order; the publisher writes to each one serially, three seconds apart, ten seconds on relay.damus.io.

### relay.damus.io

**Writing.** EVENT over WebSocket, wait for OK. Accepts events up to about 88 KB.

**Reading.** wss://relay.damus.io; the reader sends REQ with a #x filter and the author key.

**Byte exactness.** Byte exact inside the JSON content string.

**Age and retention.** Since 2022, largest reach of any relay.

**Limits.** Bans an address that writes about one event per second; the publisher waits ten seconds and sends at most five events per run.

**Failure mode.** OK false with a reason string such as rate-limited or invalid: event too large.

### nos.lol

**Writing.** Same.

**Reading.** wss://nos.lol

**Byte exactness.** Byte exact.

**Age and retention.** Since 2022, serves data back to 2024-01.

**Limits.** 64 KiB per event, so the large post is refused here.

**Failure mode.** OK false, event too large.

### nostr.oxtr.dev

**Writing.** Same.

**Reading.** wss://nostr.oxtr.dev

**Byte exactness.** Byte exact.

**Age and retention.** Old data served.

**Limits.** Raised limit, 88 KB verified.

**Failure mode.** Ordinary.

### relay.primal.net

**Writing.** Same.

**Reading.** wss://relay.primal.net

**Byte exactness.** Byte exact.

**Age and retention.** Read by every Primal client.

**Limits.** Frame 1 MB; writes timed out once in September, so the publisher logs the outcome.

**Failure mode.** Timeout rather than OK false.

### schnorr.me

**Writing.** Same.

**Reading.** wss://schnorr.me

**Byte exactness.** Byte exact.

**Age and retention.** Smaller operator, raised limits.

**Limits.** 1.3 MB frame.

**Failure mode.** Ordinary.

### relay.illuminodes.com

**Writing.** Same.

**Reading.** wss://relay.illuminodes.com

**Byte exactness.** Byte exact.

**Age and retention.** Stores 30023 events of 182 KB.

**Limits.** The most generous verified.

**Failure mode.** Ordinary.

### nostr.mom

**Writing.** Same.

**Reading.** wss://nostr.mom

**Byte exactness.** Byte exact.

**Age and retention.** Old data back to 2024-01.

**Limits.** 64 KiB.

**Failure mode.** Event too large for this post.

### purplerelay.com

**Writing.** Same.

**Reading.** wss://purplerelay.com

**Byte exactness.** Byte exact.

**Age and retention.** Old data served.

**Limits.** 64 KiB.

**Failure mode.** Event too large for this post.

### nostr-01.yakihonne.com

**Writing.** Same.

**Reading.** wss://nostr-01.yakihonne.com

**Byte exactness.** Byte exact.

**Age and retention.** The relay of a long-form client.

**Limits.** Not stated.

**Failure mode.** Ordinary.

**Writing.** Same.

## Correlated failures

Independence is the whole point of listing many hosts, so it is worth being
explicit about which ones fail together.

- The four GitHub front doors share one repository. A deleted repository takes
  all four down. A GitHub outage takes raw and Pages down and leaves the two
  CDNs serving from cache for hours.
- The Blossom servers are seven operators, but most of them are small, and a
  change in the Nostr ecosystem's funding could thin the list quickly. They do
  not share infrastructure.
- The IPFS gateways share a routing system. If the providers for a CID cannot
  be found, every gateway fails the same way at the same time. Two independent
  pins, at Lighthouse and at Fula, reduce that risk; the provider's own
  gateway, when it has one, is the most likely to succeed.
- The Arweave gateways share one chain. If the bundle was never confirmed, no
  gateway has it. Once it is confirmed, the gateways are independent operators.
- Software Heritage is one organisation. It is also the one with the clearest
  mandate to outlive the others.
- The relays are ten operators with one protocol. They do not share data, but
  they share spam filters and conventions, so a change in those can affect many
  at once.

The reader's race treats every URL as independent, which is an approximation.
The source lists are grouped so that the first few tasks started at time zero
come from different families, which is as much as a static page can do about
correlation.

## What the publisher records

For every post and every host the manifest holds the URL the reader will use,
the id the host assigned if any, and whether the publisher fetched the bytes
back and found the right hash. The report next to it lists every host that
refused, with the error text verbatim, because a refusal today is information
about tomorrow. A relay that says "event too large" is not broken; a server
that says "unauthorized" with a key that worked yesterday is.

The manifest is also the input to the real end to end test. The test reads the
links from it and loads them in three browsers, then repeats with the home host
replaced by a dead one, and records time to first render in each case. Those
numbers, next to the same measurement for a service worker based gateway, are
the argument for this design: it is faster on the first visit because it does
less.

## Closing note

Every host in this document was chosen because it is free, needs no account or
only a key the publisher generates itself, and serves bytes with the headers a
browser needs. None of them was chosen because it promises to be here in ten
years. The reader's promise is different: as long as one of them, or one that
is added later, has the bytes, a link that names the hash still works.

## Appendix B: checklists

These are the checklists the publisher runs through after each run, one per host, written out so the renderer gets a long run of nested lists.

- raw.githubusercontent.com
  - write path: A git push to a public repository
  - read path: https://raw.githubusercontent.com/GaussRun/inbrowser-magnets/main/h/<hex>.md
  - bytes unchanged: Byte exact
  - evidence of retention: As old as GitHub
  - limit: Soft rate limit per IP that shows up as HTTP 429 during bursts; a single reader never sees it
  - failure signature: HTTP 404 for a missing path, 429 when throttled, connection error when blocked at the network level
- cdn.jsdelivr.net
  - write path: Nothing
  - read path: https://cdn.jsdelivr.net/gh/GaussRun/inbrowser-magnets@main/h/<hex>.md
  - bytes unchanged: Byte exact for files under the size limit
  - evidence of retention: Since 2012
  - limit: A branch reference is cached for about 12 hours, so a brand new file may 404 for a while and then appear; a commit hash reference is immutable
  - failure signature: 404 for a path that was not there when the cache was filled, or a stale copy for a path that changed; stale copies are harmless because the hash check rejects them
- cdn.statically.io
  - write path: Nothing
  - read path: https://cdn.statically.io/gh/GaussRun/inbrowser-magnets/main/h/<hex>.md
  - bytes unchanged: Byte exact for text
  - evidence of retention: Since 2018, smaller operator than jsDelivr
  - limit: Long edge cache, about a year for a branch reference, which again is harmless because the file at a hash path never changes
  - failure signature: Same as jsDelivr
- gaussrun.github.io
  - write path: A GitHub Actions workflow that uploads the repository as a Pages artifact and deploys it
  - read path: https://gaussrun.github.io/inbrowser-magnets/h/<hex>.md
  - bytes unchanged: Byte exact
  - evidence of retention: Since 2008 as a feature
  - limit: Ten builds per hour, 1 GB site size, 100 GB bandwidth per month
  - failure signature: A 404 page that is itself HTML
- nostr.download
  - write path: PUT /upload with a kind 24242 event, t=upload, x=<hex>, expiration about an hour ahead
  - read path: https://nostr.download/<hex>
  - bytes unchanged: Byte exact
  - evidence of retention: Blobs from 400 days ago still served when probed
  - limit: None published
  - failure signature: 404 for an unknown hash, 401 for a bad authorisation, 413 for too large
- blossom.ditto.pub
  - write path: Same protocol
  - read path: https://blossom.ditto.pub/<hex>
  - bytes unchanged: Byte exact
  - evidence of retention: Over a million blobs, old blobs still served after 400 days
  - limit: 2 GB per file
  - failure signature: Ordinary
- cdn.hzrd149.com
  - write path: Same protocol; run by the author of the specification, which makes it the reference behaviour
  - read path: https://cdn.hzrd149.com/<hex>
  - bytes unchanged: Byte exact on /upload
  - evidence of retention: Since the specification exists; about 150 thousand blobs
  - limit: 2 GB per file
  - failure signature: Ordinary

## Appendix D: the notes read aloud

The same notes once more, as continuous prose, which is how they were dictated before being sorted into the six questions. This is the longest section and it is here so that a reader with a slow connection sees the renderer handle a long run of plain paragraphs.

### GitHub family

On raw.githubusercontent.com: A git push to a public repository. No account beyond the GitHub account that owns the repository, which already exists. To read, https://raw.githubusercontent.com/GaussRun/inbrowser-magnets/main/h/<hex>.md with CORS *; content type is always text/plain. Byte exact. Git stores the blob and the raw endpoint streams it. As old as GitHub. A repository deleted by its owner or by a takedown vanishes from all four front doors at once, which is the main correlated failure in this family. Soft rate limit per IP that shows up as HTTP 429 during bursts; a single reader never sees it. HTTP 404 for a missing path, 429 when throttled, connection error when blocked at the network level. All three are ordinary fetch failures.

On cdn.jsdelivr.net: Nothing. It pulls from GitHub on first request and caches at the edge. To read, https://cdn.jsdelivr.net/gh/GaussRun/inbrowser-magnets@main/h/<hex>.md with CORS *; content type guessed from the extension. Byte exact for files under the size limit; jsDelivr refuses files over 20 MB and that is far above any post. Since 2012. It has survived several changes of sponsor and edge provider. A branch reference is cached for about 12 hours, so a brand new file may 404 for a while and then appear; a commit hash reference is immutable. 404 for a path that was not there when the cache was filled, or a stale copy for a path that changed; stale copies are harmless because the hash check rejects them.

On cdn.statically.io: Nothing. Same model as jsDelivr. To read, https://cdn.statically.io/gh/GaussRun/inbrowser-magnets/main/h/<hex>.md with CORS *. Byte exact for text; Statically offers image optimisation on a different path, which is never used here. Since 2018, smaller operator than jsDelivr. Long edge cache, about a year for a branch reference, which again is harmless because the file at a hash path never changes. Same as jsDelivr. The two CDNs are listed because they are independent of each other and of GitHub Pages, even if they both depend on the repository existing.

On gaussrun.github.io: A GitHub Actions workflow that uploads the repository as a Pages artifact and deploys it. The owner has to enable Pages once in the repository settings. To read, https://gaussrun.github.io/inbrowser-magnets/h/<hex>.md; Pages sends CORS * and a content type derived from the extension. Byte exact; Pages serves the artifact as is when there is a .nojekyll file at the root. Since 2008 as a feature. The reader uses it as the home host in the test links, so the test with a dead home host is exactly the test where this one is down. Ten builds per hour, 1 GB site size, 100 GB bandwidth per month. Irrelevant at this scale. A 404 page that is itself HTML. The reader must not render it; the integrity check makes sure it does not.

### Blossom family

On nostr.download: PUT /upload with a kind 24242 event, t=upload, x=<hex>, expiration about an hour ahead. Returns a descriptor with url, sha256, size and type. To read, https://nostr.download/<hex> with CORS *, 10 GB per file limit, mirror endpoint available. Byte exact; the descriptor sha256 is checked against ours after every upload. Blobs from 400 days ago still served when probed. Best evidence among the general purpose servers. None published. The publisher waits three seconds between uploads anyway. 404 for an unknown hash, 401 for a bad authorisation, 413 for too large. Ordinary.

On blossom.ditto.pub: Same protocol. Accepts text and images from any key. To read, https://blossom.ditto.pub/<hex> with CORS * and cache-control: immutable. Byte exact; no /media endpoint, so there is no path by which it could re-encode anything. Over a million blobs, old blobs still served after 400 days. 2 GB per file. Ordinary.

On cdn.hzrd149.com: Same protocol; run by the author of the specification, which makes it the reference behaviour. To read, https://cdn.hzrd149.com/<hex> with CORS *. Byte exact on /upload; its /media endpoint re-encodes images and is never used. Since the specification exists; about 150 thousand blobs. 2 GB per file. Ordinary.

On blossom.yakihonne.com: Same protocol. Explicitly allows text/* in its upload policy. To read, https://blossom.yakihonne.com/<hex> with CORS *. Byte exact on /upload. Blobs from 120 days served, one from 250 days gone, so retention is shorter than the first three. 200 MB per file. Ordinary; the mirror endpoint refuses, which only matters for fan-out.

On blossom.nmail.li: Same protocol. To read, https://blossom.nmail.li/<hex> with CORS *. Byte exact; /media disabled. Unknown; no old blob was sampled. Not stated. Ordinary.

On blossom.jumble.social: Same protocol, but the upload preflight refuses text/markdown, so the publisher sends Markdown as text/plain. The bytes are the same; only the declared type differs. To read, https://blossom.jumble.social/<hex> with CORS *. Byte exact. Blobs from 30 days served; longer not sampled. 20 MB per file, 10 uploads per minute and 30 per hour per address. The publisher stays far below that. 429 when the per-address limit is hit; the publisher backs off and retries on the next run.

On files.sovbit.host: Same protocol. To read, https://files.sovbit.host/<hex> with CORS *. Byte exact. Unknown. 10 MB per file, 500 MB per key. Ordinary.

## Appendix E: the six questions, asked of the design itself

**What does it take to write?** One run of a Node script with one API key for IPFS pinning, one for a second pinning service, and a Nostr private key that the script generates on first use. Everything else is unauthenticated or signed with that key. The script takes a few minutes, most of it waiting between relay writes so as not to look like a bot.

**What serves the bytes back?** Between twenty and thirty URLs per post, spread over six families, every one of which sends CORS headers that let a page on any origin fetch it. The reader never needs a proxy.

**Are the bytes unchanged?** Yes, by construction. Every host is addressed by hash or verified by hash after the fact, and the browser enforces the hash on every HTTP source before the page sees the body. A host that changes a byte is simply a host that does not have the post.

**How long will it last?** Nobody knows, and the design does not need to know. The evidence collected while choosing hosts suggests years for most of them. The reader can add a source without changing the link format, and an old link benefits from a new source the moment it is deployed.

**What limits apply?** Posts stay under 107,520 bytes so the free Arweave tier takes them. Posts over about 55 KB do not fit on most relays, and the publisher knows that and records it. Nothing else is close to a limit at the scale of a personal blog.

**What is the failure mode?** Every source fails, and the reader shows the hash, the list of URLs it tried, the error from each, a copyable fallback URL and a search link. It does not redirect on its own. That page is the plain end of the road, and it is reached only when every host in six families is gone or unreachable at the same time.
