# How the link format works

[The first post](#v1.bd1a16da7322254332a1bf541f3024267347635aa059c56533ef7ccb56cbfff2.5cedf17233b099062a5c68724d24b0a42fe5be22c779553debd23fc3f06a42e4.g:GaussRun/inbrowser-magnets~o:mulihost.0rs.org) argued that a link should name the content and only hint at where copies live. [The second](#v1.cc1b13450bb6b0338d89018eba9a3a5e5d6940a1a1305d361f0d0e8ef84f9039.5cedf17233b099062a5c68724d24b0a42fe5be22c779553debd23fc3f06a42e4.g:GaussRun/inbrowser-magnets~o:mulihost.0rs.org) showed why that cannot be done at the DNS layer. This post is the reference for what we actually shipped: the exact grammar of a v1 link, the hint codes, what the reader does with them, and the one hash derivation you need to know.

## The grammar

Everything the reader needs sits after the `#`. There are two forms.

```
https://<loader-host>/<anything>#v1.<hex>[.<pub>][.<hints>]
https://<loader-host>/#@<author>/<slug>/v1.<hex>[.<pub>][.<hints>]
```

The pieces, separated by dots:

- `v1` is the version of the grammar.
- `hex` is the sha256 of the exact bytes of the Markdown file, lowercase, 64 characters. It is the only required part and it is the identity of the post.
- `pub` is optional: the author's Nostr public key, as 64 hex characters or in `npub1` form. The Nostr source uses it to query the author's long-form events, and the reader shows it in the header.
- `hints` is optional: a `~` separated list of `code:value` entries that tell the reader where copies were last known to be.

A minimal link is just the hash. With the example hash used throughout this post, this link finds the post from the built-in hosts alone:

```
https://mulihost.0rs.org/#v1.312453b85dbbece038586643c5cb220e8925b8a1700d121b37f4a9acdd70fcd0
```

The same post with the author key, the home host and the public repo as hints:

```
https://mulihost.0rs.org/#v1.312453b85dbbece038586643c5cb220e8925b8a1700d121b37f4a9acdd70fcd0.5cedf17233b099062a5c68724d24b0a42fe5be22c779553debd23fc3f06a42e4.o:mulihost.0rs.org~g:GaussRun/inbrowser-magnets~a:JpCbBtEL62oENawwQnAT5r-bw7jETYeP55s2KLqGacA
```

The reader reads only `location.hash`. The path before the `#` is ignored for lookup, which is why the first form allows `<anything>` there: a readable `/@gaussrun/how-the-link-format-works` for humans and search engines, served by whatever the loader host returns for any path.

The second form is private mode. The path is empty and the readable label moves into the fragment. The parser strips everything up to and including `/v1.` and continues as before:

```
https://mulihost.0rs.org/#@gaussrun/how-the-link-format-works/v1.312453b85dbbece038586643c5cb220e8925b8a1700d121b37f4a9acdd70fcd0.5cedf17233b099062a5c68724d24b0a42fe5be22c779553debd23fc3f06a42e4.o:mulihost.0rs.org~g:GaussRun/inbrowser-magnets
```

The label is not verified. The reader displays the author and title from the verified content and shows a warning line when the label in the link disagrees with them.

## Why nothing after the hash sign leaves the browser

A URL fragment is never sent in an HTTP request. The host serving the reader page receives `GET /` and, in the first form, the readable path, and that is all. It cannot see the hash, the author key or the hints, so it cannot log which post was read and cannot be ordered to block a single post without blocking the whole page. In private mode it cannot even see the label. This also means that any copy of the reader, on any domain, opens any link, because the copy has nothing to resolve server-side.

## The hint codes

Every hint is `code:value`. A `*` inside a value is replaced with the hash, so a host list written once covers every post an author ever publishes. A literal `*` or `~` in a value is percent-encoded as `%2A` and `%7E`. Unknown codes are ignored, and codes can be longer than one letter.

- `o:host[/base]`, the owner host. Expands to `https://host[/base]/h/*.md`.
- `g:user/repo[@branch]`, a public GitHub repo, branch `main` by default. Expands to three URLs on separate infrastructure: `https://raw.githubusercontent.com/user/repo/<branch>/h/*.md`, `https://cdn.jsdelivr.net/gh/user/repo@<branch>/h/*.md` and `https://cdn.statically.io/gh/user/repo@<branch>/h/*.md`. The Statically form with `/<branch>/` instead of `@<branch>` answers with a 301 to a plain `http://` URL, which browsers block as mixed content, so we use the `@` form.
- `t:<url>`, any URL template containing `*`, used as written, with `https://` added if the scheme is missing. Akkoma media is named by sha256, so `t:media.nuages.cloud/media/*.md` works as a template.
- `s:host`, an extra Blossom server. Expands to `https://host/<hex>`.
- `n:host`, an extra Nostr relay. Expands to `wss://host`.
- `a:<txid>`, an Arweave transaction id. Expands to `https://<gw>/raw/<txid>` for every gateway in the built-in list.
- `b:<did>[/<blobcid>]`, an AT Protocol blob. The reader resolves the DID through `plc.directory` or `did:web`, finds the PDS, and calls `com.atproto.sync.getBlob`. Without a blob CID it uses the raw CIDv1 of the hash, because a PDS mints exactly that CID for an uploaded blob.
- `u:<url>`, one literal URL for this post, for hosts whose URL cannot be derived from the hash. Pleroma inserts a uuid per upload, so a Pleroma copy is `u:media.pl.chipmunk.land/media/<uuid>/<hex>.md` with the real uuid written out.
- `ns:<npub>`, an nsite under that key. Expands to `https://<npub>.<gw>/h/*.md` for the gateways `nsite.lol`, `nwb.tf` and `nosto.re`.

The `/h/<hex>.md` convention is the contract between the publisher and the reader: on every host that follows it, a post lives at a path derived from its own hash, so the link only has to carry the host.

## From link to race

Parsing is the easy part. The reader then has to turn one hash and a handful of hints into a list of requests and run them without waiting for anything.

First it derives the two forms of the digest it needs: `hex` for paths, Blossom and the final comparison, and the CIDv1 for IPFS and Bluesky. Then it collects every source, built-in and hinted, and sorts the tasks into priority bands:

- 10: Blossom servers, built in and from `s:` hints, and nsite gateways from `ns:`
- 12: Arweave gateways by transaction id from `a:`
- 14: Software Heritage, `https://archive.softwareheritage.org/api/1/content/sha256:<hex>/raw/`
- 16: Nostr relays
- 20: the owner host from `o:` and literal URLs from `u:`
- 30: the GitHub-derived URLs from `g:` and templates from `t:`
- 40: IPFS gateways, `https://<gw>/ipfs/<cid>?format=raw`
- 50: Bluesky PDS blobs from `b:`
- 60: Arweave GraphQL lookup by the `Content-SHA256` tag, when there is no transaction id

![Priority bands: which hosts the reader asks first](sha256:5031481b7bbce894c1926bde714a945b19a97d797e795342ff2d2654af214ae3)

Hosts that need no signup and are addressed by the hash alone come first, because they are the ones that will still be there when the author's own accounts are gone. The owner host comes after them, not before, even though it is the most likely to be fast: if it is dead, nothing was lost, and if it is alive, the Blossom servers are usually faster anyway. IPFS is kept on principle and sits late, after the 2026 retirement of the big public gateways. The reader remembers the latency of past winners in localStorage and may promote a URL within its band, never across bands.

The race itself is small:

1. Start the first three tasks at t=0. With the built-in lists that is three Blossom servers.
2. Every 300 ms, add two more, up to eight in flight. At 300 ms that is Arweave and Nostr; at 600 ms the owner host and GitHub.
3. Each HTTP task is a plain `fetch(url, { mode: 'cors', signal })`. The reader hashes the bytes it gets with `crypto.subtle` and compares the result with `hex`; nothing is rendered before that comparison passes. We tried the browser's `integrity` option first and dropped it: a mismatch then rejects with the same generic `TypeError` as a network failure, which would hide a tampering mirror in the failure list. Active sources, Nostr and Bluesky, fetch their own bytes and go through the same hash check.
4. The first task that resolves wins. Every other task is aborted through its own `AbortController`. The winner's source and latency are recorded.
5. If every task fails, the reader shows the hash, the full list of URLs it tried with the error for each, a copyable `inbrowser.link` URL and a search link. It never redirects on its own.

Verified bytes are cached in IndexedDB by hash and rendered in a sandboxed iframe with no script permission. A tampered mirror listed first is not a special case: its bytes fail the hash check, the failure list says `hash mismatch` for that URL, and the race continues.

## From sha256 to CID

IPFS and Bluesky do not speak sha256 hex. They speak CIDs. For a file stored as a single raw block, which every post is, the CIDv1 is nothing more than the digest with a header in front, so the reader derives it instead of asking anyone.

Take the four prefix bytes `01 55 12 20`: CID version 1, the `raw` codec, the `sha2-256` hash function, and the digest length of 32 bytes. Append the 32 bytes of the digest. Encode the 36 bytes in base32 with the alphabet `abcdefghijklmnopqrstuvwxyz234567`, no padding, and put a `b` in front to mark the base. Because the prefix bytes are constant, every such CID starts with `bafkrei`.

For the example hash:

```
hex: 312453b85dbbece038586643c5cb220e8925b8a1700d121b37f4a9acdd70fcd0
cid: bafkreibrerj3qxn35tqdqwdgipc4wiqores3rilqbujbwn7uvgwn24h42a
b64: MSRTuF277OA4WGZDxcsiDokluKFwDRIbN/SprN1w/NA=
```

This works for files up to 1 MiB as a single raw block. Posts stay under 107,520 bytes anyway, which is the limit of the Arweave Turbo free tier, so one hash is at the same time the Blossom path, the Software Heritage key, the Arweave tag value, the IPFS CID and the Bluesky blob CID. The conversions are pure functions in `src/hash.js`, and the reverse direction, CID back to hex, is the same operation backwards.

## What a publisher writes

For the reader to find a post, the publisher writes the exact bytes once and puts them wherever it can: `/h/<hex>.md` on the home host and in the public repo, the blob on Blossom servers, an Arweave upload with a `Content-SHA256` tag, a Nostr event carrying the hash. The link then carries the hash, the author key, and the hints for the hosts that cannot be derived from the hash: `o:`, `g:`, `a:`. Everything else the reader finds on its own, and any of those hints can rot without the link breaking.
