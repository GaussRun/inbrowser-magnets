# How the reader races the hosts

This is the medium test post for inbrowser-magnets. It is about twenty
kilobytes long and it exercises the parts of the Markdown renderer that the
small post does not: nested lists, fenced code, blockquotes, tables of plain
text, an image fetched over plain HTTPS and an image referenced by its sha256.

![A small horseshoe magnet, served by hash](sha256:95c8b6c778a3566aeb03e042415ceda09df2cd5f8dfb3eba5c081b104fbeffae)

The image above is not loaded from a URL. The reader sees the `sha256:` scheme,
runs the same race it ran for this post, and turns the winning bytes into a
`blob:` URL. The image below is an ordinary HTTPS image and is loaded lazily.

![The same magnet, served from the GitHub raw mirror](https://raw.githubusercontent.com/GaussRun/inbrowser-magnets/main/h/95c8b6c778a3566aeb03e042415ceda09df2cd5f8dfb3eba5c081b104fbeffae.png)

## The problem in one paragraph

A blog post is a few kilobytes of text. Keeping it online for ten years is not
a storage problem; a phone could hold every post ever written on a personal
blog. It is a naming problem. The name people share is a URL, and a URL names a
machine, a domain registration, a hosting bill and a legal jurisdiction. When
any of those changes, the name stops working, even though a thousand copies of
the bytes still exist on disks around the world.

The reader turns this around. The name is the hash of the bytes. Where the
bytes live is a hint, not a promise. The page that renders the post is itself a
static file that can be copied anywhere, and it does not care which copy of
itself is running.

## What happens when you open a link

1. The browser loads a static HTML page from whatever host is in the link.
2. The page reads `location.hash`. The path is ignored.
3. From the fragment it takes the version, the sha256, an optional author key
   and a list of hints.
4. It derives three forms of the same digest:
   - lowercase hex, used in paths such as `/h/<hex>.md`;
   - standard base64, used for `integrity: 'sha256-<b64>'`;
   - a CIDv1 raw block id, used on IPFS gateways.
5. It expands the hints and the built-in lists into a flat list of URLs.
6. It starts the first three fetches at once, adds two more every three
   hundred milliseconds, and never has more than eight in flight.
7. The first response whose bytes hash to the expected value wins. Every other
   request is aborted.
8. The bytes are rendered into a sandboxed iframe and cached in IndexedDB.

No service worker is registered. No peer to peer protocol is spoken. Each
source costs exactly one HTTPS GET, and the browser's own `integrity` check
rejects a tampered mirror before a single byte reaches the page's JavaScript.

> The point of the race is not speed for its own sake. It is that the reader
> never has to decide which host to trust. It trusts the hash, and it lets the
> hosts compete to be first.

## Sources, in priority order

The reader keeps a small static table of sources. Each one is either an HTTP
source, which only produces URLs, or an active source, which fetches on its own
and hands back bytes that the core verifies again.

| Source | Kind | Needs a hint | Typical latency |
| --- | --- | --- | --- |
| owner host | http | `o:` | 50 to 300 ms |
| GitHub raw, jsDelivr, Statically | http | `g:` | 100 to 400 ms |
| Blossom servers | http | no | 100 to 800 ms |
| IPFS gateways | http | no | 300 ms to 6 s |
| Arweave gateways | http | `a:` | 200 ms to 2 s |
| Software Heritage | http | no | 500 ms to 3 s |
| Nostr relays | active | no | 300 ms to 2 s |
| Bluesky blob | active | `b:` | 300 ms to 2 s |

The table is static data. The order inside each group is only the initial
guess; the reader remembers which source won last time and how long it took,
and it moves the fastest ones to the front on the next visit.

### Why hash-only sources matter most

A hint in the link is a promise made by the author at publishing time. A
hash-only source is a promise made by the protocol. Blossom servers serve any
blob at `https://<host>/<sha256>`. IPFS gateways serve any raw block at
`/ipfs/<cid>?format=raw`. Software Heritage serves any archived file at
`/api/1/content/sha256:<hex>/raw/`. Nostr relays answer a tag query for
`#x` with the sha256. None of those need to know who the author is or where
the post was first published. A link with no hints at all still resolves, as
long as somebody, anybody, put the bytes on one of those networks.

## The link grammar

A link looks like this:

```text
https://gaussrun.github.io/inbrowser-magnets/#v1.<hex>.<pub>.g:GaussRun/inbrowser-magnets~o:gaussrun.github.io/inbrowser-magnets
```

The pieces after the `#` are separated by dots:

- `v1` is the grammar version;
- `<hex>` is the sha256 of the Markdown bytes;
- `<pub>` is the author's Nostr public key, optional;
- everything after that is a `~` separated list of `code:value` hints.

A hint value may contain `*`, which is replaced by the hex. So the template
hint `t:example.org/posts/*.md` expands to
`https://example.org/posts/<hex>.md`. Literal `*` and `~` are percent-encoded.

There is also a labelled form for people who want the link to say what it is:

```text
https://gaussrun.github.io/inbrowser-magnets/#@gaussrun/medium-post/v1.<hex>.<pub>.g:GaussRun/inbrowser-magnets
```

The label is only for humans and for the address bar. If it disagrees with the
author or title found inside the content, the reader shows a warning line but
still renders the post, because the bytes matched the hash and that is the only
thing that counts.

### Parsing it

The parser is a pure function. It takes the fragment string and returns the
version, the hex, the optional key, the hints and the label, or it throws.

```js
export function parseFragment(hash) {
  let s = hash.startsWith('#') ? hash.slice(1) : hash;
  let label = null;
  if (s.startsWith('@')) {
    const at = s.indexOf('/v1.');
    if (at < 0) throw new Error('bad label');
    const [author, slug] = s.slice(1, at).split('/');
    label = { author, slug };
    s = s.slice(at + 1);
  }
  const parts = s.split('.');
  if (parts[0] !== 'v1') throw new Error('bad version');
  const hex = parts[1];
  if (!/^[0-9a-f]{64}$/.test(hex)) throw new Error('bad hash');
  let pub = null;
  let rest = parts.slice(2);
  if (rest[0] && (/^[0-9a-f]{64}$/.test(rest[0]) || rest[0].startsWith('npub1'))) {
    pub = rest[0];
    rest = rest.slice(1);
  }
  const hints = rest.join('.').split('~').filter(Boolean).map((h) => {
    const i = h.indexOf(':');
    return { code: h.slice(0, i), value: decodeURIComponent(h.slice(i + 1)) };
  });
  return { v: 1, hex, pub, hints, label };
}
```

The function above is illustrative. The real one lives in `src/link.js` and
has unit tests for every malformed input the author could think of.

## Three forms of one digest

The hex form is the one in links and in file names. The base64 form is what
the browser wants in the `integrity` attribute. The CID form is what IPFS
gateways want in the path. All three are the same thirty-two bytes.

```js
const PREFIX = [0x01, 0x55, 0x12, 0x20]; // CIDv1, raw codec, sha2-256, 32 bytes
const ALPHABET = 'abcdefghijklmnopqrstuvwxyz234567';

export function hexToCid(hex) {
  const bytes = new Uint8Array(36);
  bytes.set(PREFIX, 0);
  for (let i = 0; i < 32; i++) bytes[4 + i] = parseInt(hex.slice(i * 2, i * 2 + 2), 16);
  let bits = 0, value = 0, out = 'b';
  for (const b of bytes) {
    value = (value << 8) | b;
    bits += 8;
    while (bits >= 5) {
      out += ALPHABET[(value >>> (bits - 5)) & 31];
      bits -= 5;
    }
  }
  if (bits > 0) out += ALPHABET[(value << (5 - bits)) & 31];
  return out;
}
```

A raw CID is valid for any file up to one mebibyte stored as a single block.
Test posts are kept under 107,520 bytes anyway, because that is the free
upload limit on the Arweave Turbo service, and it is convenient when every
host accepts every post.

## What "free" means here

Every host used for the test posts is free and needs no account:

- **GitHub** serves a public repository through four different domains:
  `raw.githubusercontent.com`, `cdn.jsdelivr.net`, `cdn.statically.io` and
  GitHub Pages. One push, four origins.
- **Blossom** servers accept a blob from any Nostr key that signs a small
  authorisation event. The blob is addressed by sha256, so the uploader's
  identity does not matter for retrieval.
- **IPFS** pinning on Lighthouse is free up to five gigabytes, with an API key
  obtained by signing a message with a wallet, and public gateways run by
  Filebase, Pinata, 4EVERLAND, Blockfrost, Aleph and PinMe serve the block.
- **Arweave** through Turbo accepts items under 105 KiB for free, without a
  signature, and they are permanent.
- **Software Heritage** archives any public git repository on request and
  serves every file in it by hash.
- **Nostr** relays accept long-form events from any key, within size limits.

None of these is a promise of eternity. Each one can go away. The design
assumption is that they will not all go away in the same week, and that the
reader can add new ones later without breaking old links, because old links
name the hash, not the host.

### What is not free

Two things cost something:

1. the author's time to run the publisher once per post;
2. the reader's bandwidth for the losing requests, which are aborted early and
   usually transfer nothing beyond headers.

The first is a few seconds. The second is a few kilobytes.

## Failure modes the tests cover

The reader is tested against a set of local mock servers before it is tested
against real hosts. The mocks imitate the home host, a GitHub raw mirror, a
Blossom server and an IPFS gateway, and one of them deliberately serves wrong
bytes. The test cases are:

- every mock is healthy, the post renders;
- the home host returns 404, the post renders from a mirror;
- the home host returns a seizure notice as HTML, the post renders from a
  mirror and the seizure page never touches the DOM;
- the home host refuses the connection, the post renders;
- the tampering mirror is listed first, it is rejected by `integrity` and the
  post renders from the next source;
- every mirror is down, the reader shows the hash, every URL it tried with the
  error it got, a copyable fallback URL and a search link, and it does not
  redirect anywhere on its own;
- the label in the link disagrees with the content, a warning line appears.

Each case records time to first render. The numbers from the mocks are not the
numbers from the real world, but they catch regressions in the race logic, and
the real run against the published copies of this post gives the real numbers.

## Rendering

The Markdown subset is deliberately small: ATX headings, paragraphs, emphasis,
inline code, fenced code, links, images, ordered and unordered lists,
blockquotes and horizontal rules. Raw HTML in the source is escaped, never
passed through. The result goes into an iframe with an empty `sandbox`
attribute, so no script runs and the frame has no origin of its own. Links open
in the top window with `rel="noopener"`.

Front-matter is a YAML subset of three keys:

```yaml
---
title: How the reader races the hosts
author: GaussRun
date: 2026-10-23
---
```

Anything else in the front-matter is ignored. The title and author appear in
the header above the frame, next to the name of the source that won, its
latency, a verified badge, the full hex and a copy button.

## A note on size

Relays are the only source with a meaningful size limit. Most free relays
refuse events over sixty-four kibibytes of JSON, and Markdown grows a little
when it is escaped into a JSON string. This post fits with room to spare. The
large test post does not, and the publisher records which relays took it and
which refused it with "event too large". That is fine: the large post still
has six other kinds of host, and the relay copy was never the primary one.

The hash of this file is in the link you used. The publisher computed it once,
wrote the file to disk, and pushed the same bytes everywhere. If any host had
changed a single byte, even a trailing newline, its copy would be worthless,
and the reader would have moved on to the next one without telling you.

## The built-in lists

For the record, these are the hash-only hosts the reader knows about without
any hint, as of the day this post was published. They are plain data and will
be edited over time; a host that disappears is removed with a note, a host
that appears is added at the end.

### Blossom servers

- `nostr.download`, a route96 instance with the best long-term evidence among
  general purpose servers
- `blossom.ditto.pub`, 1.4 million blobs, `cache-control: immutable`
- `cdn.hzrd149.com`, run by the author of the Blossom specification
- `blossom.yakihonne.com`, explicitly accepts `text/*`
- `blossom.nmail.li`
- `blossom.jumble.social`, ten uploads per minute per address
- `files.sovbit.host`, ten megabytes per file

The URL shape is always `https://<host>/<hex>`. Some servers also accept an
extension after the hex, which helps browsers pick a content type, but the
reader never needs it because it treats every response as bytes.

### IPFS gateways

- `ipfs.filebase.io`
- `gateway.pinata.cloud`
- `ipfs.4everland.io`
- `ipfs.blockfrost.dev`
- `ipfs.aleph.cloud`
- `gateway.pinme.dev`

The URL shape is `https://<gateway>/ipfs/<cid>?format=raw`. The query string
asks for the raw block instead of a UnixFS interpretation, which is what makes
the sha256 check meaningful: the raw block is the file, byte for byte.

### Arweave gateways

- `arweave.net`
- `ar-io.dev`
- `turbo-gateway.com`
- `ardrive.net`

These are only used when the link carries an `a:` hint with the transaction
id, because Arweave is addressed by transaction, not by content hash. When
there is no hint, the reader can still ask the GraphQL index for a transaction
tagged `Content-SHA256` with our hex, which costs one extra round trip.

### Nostr relays

- `relay.damus.io`
- `nos.lol`
- `nostr.oxtr.dev`
- `relay.primal.net`
- `schnorr.me`
- `relay.illuminodes.com`
- `nostr.mom`
- `purplerelay.com`
- `nostr-01.yakihonne.com`
- `relay.nos.social`

The relay source is active rather than HTTP: it opens a WebSocket, sends one
`REQ` with a `#x` filter for the hex, and takes the content of the first kind
30023 event whose content hashes correctly. It is loaded lazily, after the
HTTP sources have had a head start, because it is the slowest to set up.

## Publishing checklist

The publisher is a single Node script. For each post it does the following,
in this order, and records the result of every step in a manifest:

1. Read the bytes, compute hex, base64 and CID.
2. Write `h/<hex>.md` into the public repository, commit, push, and wait for
   GitHub Pages to pick it up.
3. Sign a Blossom authorisation event and `PUT` the bytes to each server,
   three seconds apart, checking that the returned descriptor carries our
   sha256 and not some re-encoded variant.
4. Upload the bytes to Arweave through Turbo with `Content-Type` and
   `Content-SHA256` tags and keep the transaction id.
5. Upload the bytes to Lighthouse as a CIDv1 raw block and compare the
   returned CID with ours; then ask a second pinning service to pin the same
   CID so the block has two independent providers.
6. Publish a kind 30023 event to each relay, one event every three seconds,
   ten on the busiest relay, and keep the event id and the list of relays that
   answered `OK`.
7. Ask Software Heritage to archive the public repository.
8. Fetch every URL back, hash the bytes, and mark the ones that matched.

The script is idempotent. Running it again reads the manifest, skips anything
already verified, and retries only what failed. That matters because free
hosts have bad days, and the right response to a bad day is to try again
tomorrow, not to give up on the host.

## Glossary

- **blob**: a sequence of bytes with no interpretation, named by its hash.
- **CID**: content identifier, the IPFS name for a blob; the raw variant is a
  thin wrapper around a sha256 digest.
- **hint**: a short code in the link telling the reader about one more place
  to look.
- **integrity**: the browser attribute that makes `fetch` reject a response
  whose hash does not match.
- **magnet**: a link that names content by hash rather than by location.
- **race**: starting several fetches at once and keeping the first good one.
- **relay**: a Nostr server that stores and forwards signed events.
- **seizure**: the case where a domain is taken over and serves a notice
  instead of the content; the reader treats it like any other wrong answer.

## Questions people ask

**Why not just use IPFS?** The reader does use IPFS, as one family of hosts
among six. Using only IPFS would mean depending on one routing system and on
gateways that have been retired twice in the last few years. It would also
mean a slower first load, because an in-browser IPFS client has to be
downloaded and started before it can fetch anything. The reader's first fetch
starts before its own script has finished parsing.

**Why not a service worker?** A service worker is useful for the second visit
and useless for the first, and the first visit is the one that matters when a
link is shared. The reader is designed so that a service worker could be added
later to cache the loader itself, but the race does not depend on it.

**What if the hash in the link is wrong?** Then nothing renders, and the
failure panel shows the hash and every URL that was tried. A wrong hash is
indistinguishable from a post that was never published, which is the right
behaviour: the link is the claim, and the claim was not met.

**Can the author edit a post?** Not under the same link. An edit is a new
file with a new hash and a new link. The old link keeps pointing at the old
bytes for as long as any host has them. The Nostr kind 30023 event, which is
replaceable by its `d` tag, is the one place where an author can say "this
slug now means these bytes", and the reader shows that as a hint, not as the
content.

**Why GitHub Pages as the home host?** Because it is free, because the link
format needs some host to serve the loader page, and because it is a good
example of a host that may be unavailable: the test suite includes a run where
the home host is replaced by a dead one, and the post must still render.
