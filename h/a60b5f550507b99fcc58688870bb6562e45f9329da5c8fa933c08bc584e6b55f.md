# Why IPFS is last

IPFS is the system most people name first when they hear "content-addressed". It is also the source our reader tries last, and the one we keep only on principle. This post explains both halves of that sentence with the numbers from our test run.

## A CID from a sha256, for free

A raw IPFS block is addressed by the multihash of its bytes. For a sha2-256 raw block the CIDv1 is four prefix bytes followed by the digest:

```text
01        CIDv1
55        codec: raw
12        multihash: sha2-256
20        digest length: 32 bytes
<32 bytes of sha256>
```

The string form is `b` followed by the base32 lowercase encoding of those 36 bytes, with no padding. Every such CID starts with `bafkrei`. Because the digest is the file's sha256, the reader can compute the CID from the hash in the link with no network access and no extra identifier. For the smallest test post, sha256 `312453b85dbbece038586643c5cb220e8925b8a1700d121b37f4a9acdd70fcd0` becomes `bafkreibrerj3qxn35tqdqwdgipc4wiqores3rilqbujbwn7uvgwn24h42a`.

The derivation holds only for a single raw block, and a raw block can be at most 1 MiB. Our posts are under 107,520 bytes because of the Arweave limit from [the previous post](#v1.f8041baad05bbff69e815751e7a731312febe4c3d2e26fe51ff112e2058b1644.5cedf17233b099062a5c68724d24b0a42fe5be22c779553debd23fc3f06a42e4.g:GaussRun/inbrowser-magnets~o:mulihost.0rs.org), so every post is one block and the sha256 and the CID name the same bytes. Had we let the pinning service chunk files into a UnixFS DAG, the root CID would be a hash of a tree, unrelated to the file's sha256, and the reader could not derive it.

## Pinning: one of three worked

We tried three pinning services.

Lighthouse: its API key is obtained by signing a message with a wallet key, no email, no form. `uploadBuffer` with `cidVersion: 1` returned exactly the computed `bafkrei` CID for all four files, so the service stored each file as one raw block and no CAR upload was needed. This is the only pinning path that is fully scriptable from nothing.

Fula (cloud.fx.land): `POST /pins` answered an nginx 502 after about 90 s on every attempt, while `GET /pins` on the same API worked. No pin.

Pinata: pin-by-CID was refused with HTTP 403 and the body `{"error":{"reason":"PAID_FEATURE_ONLY","details":"You must be on a paid plan to pin by CID"}}`. No pin.

The wider research found the same pattern across the market. Filebase, Pinata, Blockfrost and 4EVERLAND each want an email or a wallet plus an identity step before the first API call; several cap free accounts at 500 files. Storacha, IPFS.NINJA, Infura IPFS and Fleek are gone. Every one of these services needs a human to sign up once, which is the line the project draws: a host that needs a human signup may be added, but neither the publisher nor the reader may depend on it.

## Gateways: slow to find a fresh block

The reader asks five public gateways for `https://<gw>/ipfs/<cid>?format=raw`, in this order:

- ipfs.filebase.io
- ipfs.blockfrost.dev
- ipfs.aleph.cloud
- gateway.pinata.cloud
- ipfs.4everland.io

A sixth, gateway.pinme.dev, was in the list during the test run and is gone now, for the reason given below.

`?format=raw` asks for the block bytes as `application/vnd.ipld.raw`, which is what the hash check needs. We prefer the query parameter over an `Accept` header because at least one CDN cached the header variant without its CORS header.

Within the first hour after pinning on Lighthouse, this is what came back for each file, with the publisher's own gateway (ipfs.cloud.fx.land, which 404s for anything it does not hold) as a seventh:

- 995 byte post: 1 of 7 gateways served it (ipfs.blockfrost.dev)
- 18,468 byte post: 1 of 7 (ipfs.aleph.cloud)
- 98,125 byte post: 0 of 7
- 203 byte PNG: 3 of 7 (ipfs.filebase.io, ipfs.blockfrost.dev, ipfs.aleph.cloud)

The failures are instructive. gateway.pinme.dev answered 500 with `block was not found locally (offline)`, which means it does not look beyond its own store at all, so we removed it from the list: a gateway that never fetches cannot serve a block it was not given. ipfs.4everland.io returned a Cloudflare 504 page. gateway.pinata.cloud timed out without a response. ipfs.filebase.io reported `timeout occurred after finding 12 provider(s) and connecting to 12 (phase: connecting to providers)`, and ipfs.aleph.cloud said the same with one provider. Those two messages are the clearest picture of what an IPFS gateway does for a block it has never seen: find providers through the DHT or an index, connect to each, ask for the block, and give up when the clock runs out. The gateway timeouts are longer than the reader is willing to wait.

The situation got worse this autumn. The commons gateways ipfs.io and dweb.link were retired on 2026-09-21 and now answer 429 with a `sunset` header; cloudflare-ipfs.com no longer resolves. What remains are the gateways run by pinning providers, which are fast for content they hold and slow for everything else, plus a few community gateways behind Cloudflare. Most of the surviving ones share Cloudflare as a front, so we keep ipfs.filebase.io (its own edge) and ipfs.blockfrost.dev (BunnyCDN) in the list for operator diversity.

## Band 40, kept on principle

The reader sorts sources into bands and IPFS is band 40: behind Blossom, Arweave by txid, Software Heritage, Nostr relays, the owner host and the GitHub mirrors. A reader following a link from [the one-link post](#v1.bd1a16da7322254332a1bf541f3024267347635aa059c56533ef7ccb56cbfff2.5cedf17233b099062a5c68724d24b0a42fe5be22c779553debd23fc3f06a42e4.g:GaussRun/inbrowser-magnets~o:mulihost.0rs.org) will almost never see the IPFS requests start, because a Blossom server answers within the first few hundred milliseconds and the race aborts everything else.

We keep IPFS anyway, for two reasons. The first is that the CID costs nothing: it is derived from the hash, so five more candidate URLs are available to every link ever written, with no hint and no publisher cooperation. If a post is pinned anywhere in the future, by us or by a reader, those URLs start working retroactively. The second is that IPFS is the only one of our sources with a client-side network layer, and that matters for the last resort below.

What we will not do is move it up. A source whose typical answer for fresh content is a 504 after a long wait cannot sit in the first wave without making every page load slower, and a source that depends on a signup cannot be required. The band is where the measurements put it.

## The last-resort button

When every source fails, the reader shows the hash, the full list of URLs it tried with their errors, and one more thing: a button for `https://<cid>.ipfs.inbrowser.link/`. It is a button, not a redirect. The reader never follows it on its own.

inbrowser.link is a service worker gateway. Loading it installs a service worker in your browser that speaks the IPFS block protocol, finds providers, fetches blocks and verifies them locally. It refuses non-browser clients with 403 and it needs a first visit to install the worker before it can serve anything. It is a real IPFS node in a tab, and it is the one way to retrieve a block when no HTTP gateway will, provided somebody still provides it.

That is also why it is the opposite of how our reader loads. The reader is a static page that makes one HTTPS GET per source, hashes whatever comes back and compares it with the link, races the sources, and aborts the losers. No service worker, no peer discovery, no protocol beyond HTTPS, so the first visit on a fresh browser is as fast as any later one. inbrowser.link pays for its generality with a slower first load and a dependence on providers being reachable from the browser. The two are complementary: ours is for the ordinary case, theirs is for the case where the ordinary web has let a post go. We want that door to exist, and we want a human to decide to open it.

## Summary

- The CID is free: `01 55 12 20` plus the sha256, base32, `bafkrei`, valid for one raw block up to 1 MiB.
- Lighthouse pins without a signup and returns the derived CID. Fula and Pinata did not pin anything.
- Public gateways found a fresh block in at most 3 of 7 attempts per file in the first hour, and the 98 KB post in none.
- Band 40, on principle; never required, never first.
- inbrowser.link is the last resort, offered as a button and never followed automatically.
