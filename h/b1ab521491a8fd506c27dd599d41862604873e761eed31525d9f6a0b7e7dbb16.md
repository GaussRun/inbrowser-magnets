# Blossom servers that take text

If we had to keep exactly one host type, it would be Blossom. A Blossom server stores blobs and serves each one at `https://<server>/<sha256>`. The URL is the hash. There is no account to create, no file name to agree on, no index to query. The reader described in [the one-link post](#v1.bd1a16da7322254332a1bf541f3024267347635aa059c56533ef7ccb56cbfff2.5cedf17233b099062a5c68724d24b0a42fe5be22c779553debd23fc3f06a42e4.g:GaussRun/inbrowser-magnets~o:mulihost.0rs.org) already has the hash, so it can build the URL for every server it knows and start fetching at once.

## BUD-01 and BUD-02 in two sentences

The Blossom specification is a set of short documents called BUDs. BUD-01 says: `GET /<sha256>` returns the blob, an optional file extension may follow the hash, `HEAD` works, and the server sends `Access-Control-Allow-Origin: *`. BUD-02 adds uploads: `PUT /upload` with the raw bytes as the body and a Nostr event in the `Authorization` header, and the rule that the server "MUST NOT modify the blob in any way and MUST compute the sha256 hash over the exact bytes received".

That second rule is why Blossom fits a hash-addressed reader and most upload APIs do not. The server has no business touching the bytes, and the descriptor it returns names the sha256 it computed, so the publisher can compare that to its own hash and treat any difference as a failed upload.

## The authorisation event

The `Authorization` header is `Nostr <base64 of a signed kind 24242 event>`. Ours looks like this before signing:

```json
{
  "kind": 24242,
  "content": "upload <hex>.md",
  "tags": [
    ["t", "upload"],
    ["x", "<hex>"],
    ["expiration", "<unix time, 600 s ahead>"]
  ]
}
```

The `x` tag binds the token to one blob, so a leaked token cannot upload something else. The request also carries `Content-Type`, `X-SHA-256` with the same hex, and `Content-Length`. The key that signs the token does not matter for integrity, since every read is verified by hash; we sign with the author key so the blobs show up under the same pubkey as the kind 30023 events from [the relay post](#v1.ba49920232c357ae703feee8e049a1b07cbc391487c3bb5bf7b6dfefe9362aa9.5cedf17233b099062a5c68724d24b0a42fe5be22c779553debd23fc3f06a42e4.g:GaussRun/inbrowser-magnets~o:mulihost.0rs.org), but a separate upload key would work equally well.

Two things we never do. We never use `PUT /media` (BUD-05): on several servers that endpoint re-encodes images to webp, which changes the hash. And we never use the older NIP-96 upload API for anything whose hash matters, for the same reason.

## Seven servers, four files, zero refusals

We uploaded three posts of 995, 18,468 and 98,125 bytes and one 203 byte PNG to seven servers:

- nostr.download
- blossom.ditto.pub
- cdn.hzrd149.com
- blossom.yakihonne.com
- blossom.nmail.li
- blossom.jumble.social
- files.sovbit.host

All 28 uploads were accepted. The returned descriptor carried our sha256 every time. We then fetched each blob back with an `Origin` header and checked three things: the body hashed to the expected value, the byte count matched, and the response carried `access-control-allow-origin: *`. All 28 reads passed. That is the whole reason this list is the built-in Blossom list in the reader.

One quirk. blossom.jumble.social answers the BUD-06 upload preflight with 404 for `text/markdown` and accepts the same bytes as `text/plain`. The publisher sends `text/plain` there and `text/markdown` everywhere else. The stored bytes are identical, and the reader never looks at the content type, so this costs nothing.

## Limits and retention, as far as anyone states them

The read-only research in the weeks before the run collected what each server publishes about itself. Per-file limits:

- nostr.download: 10 GB per file (from its NIP-96 document), 200 MB preflight accepted
- blossom.ditto.pub: 2 GB, about 1.46 million blobs stored, serves blobs with `cache-control: immutable`
- cdn.hzrd149.com: 2 GB, run by the author of the Blossom specification
- blossom.yakihonne.com: 200 MB, explicitly accepts `text/*`
- blossom.nmail.li: no stated limit
- blossom.jumble.social: 20 MB per file, 10 uploads per minute and 30 per hour per IP
- files.sovbit.host: 10 MB per file, 500 MB total quota

Retention is the weak point. No server in this list publishes a retention policy. The only Blossom server that states one at all is 24242.io, an image host not in our list, which deletes blobs not accessed for 60 days. What we have instead is sampling: Blossom URLs found in old public notes, fetched again at probe time. nostr.download served 6 of 6 blobs from 30 days back, 1 of 1 from 250 days and 1 of 1 from 400 days. blossom.ditto.pub served 6 of 6 at 30 days, 2 of 2 at 120 days and 1 of 1 at 400 days. blossom.yakihonne.com served 6 of 6 at 30 days and 1 of 1 at 120 days, but 0 of 1 at 250 days. Of 33 Blossom server names probed, 3 were down or gone. So we assume any single server may lose a blob, and we rely on seven of them plus the hosts in the other posts to make that irrelevant for the reader.

## Why Blossom is the first band

The reader orders its sources into priority bands and starts the race with the lowest band. Blossom is band 10, together with nsite gateways. The reasons, in the order we weighed them:

1. The URL is derivable from the hash alone. No hint in the link, no lookup, no index. A link with nothing but `v1.<hex>` already has seven candidate URLs.
2. No signup. The publisher needs a Nostr key it generated itself and nothing else, which is the host priority principle behind the whole project: hosts that need a human signup may help but must never be required.
3. CORS is part of the specification and held on every read we made.
4. Latency is ordinary CDN latency. These are small static servers answering a GET, with no gateway resolution in between.

The race starts three tasks at time zero and adds two more every 300 ms, up to eight in flight. Because Blossom fills band 10, those first three requests go to three Blossom servers. Within the band, the reader remembers which server answered fastest last time (localStorage key `im.lat`) and asks that one first next time; remembered latency never moves a server across bands. The first response whose bytes hash to the hex wins, and everything else is aborted.

## Extra servers through the link

The built-in list is static. A link can add servers with the `s:` hint from [the link format post](#v1.5b9263cbfcc93c7222b1459a781f871e335adf7444e2ddf21c4e4dded1ee2de5.5cedf17233b099062a5c68724d24b0a42fe5be22c779553debd23fc3f06a42e4.g:GaussRun/inbrowser-magnets~o:mulihost.0rs.org): `s:blossom.example.org` expands to `https://blossom.example.org/<hex>` and joins band 10 alongside the built-in seven. We use it for a post that lives on an author's own Blossom server, or to keep a link working when a server has been added to the list after the reader was built.

The author's kind 10063 event (the BUD-03 server list) names the same servers in preference order, so Nostr clients and nsite gateways can find the blobs from the npub alone. The reader does not read kind 10063; it only needs the hash.

## What Blossom does not solve

Blossom gives us a hash-addressed store with no account and good CORS, run by a handful of volunteers with no durability promise. The research found 6 more servers that passed the text preflight but were never write-tested, and a dozen media-only servers that reject `text/markdown` with 400 or 415. We will add servers once a real upload and read-back succeed, and we will drop one only after noting why, because a reader built a year ago still has the old list baked in. The long-term copy is the subject of the next post, on Arweave.
