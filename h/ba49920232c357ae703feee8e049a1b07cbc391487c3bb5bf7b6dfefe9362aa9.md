# Nostr relays and the 64 KB limit

Nostr relays are the odd one out among our sources. Every other host answers a plain HTTPS GET. A relay is a WebSocket that stores signed JSON events and answers filter queries. It still fits the model from [the one-link post](#v1.bd1a16da7322254332a1bf541f3024267347635aa059c56533ef7ccb56cbfff2.5cedf17233b099062a5c68724d24b0a42fe5be22c779553debd23fc3f06a42e4.g:GaussRun/inbrowser-magnets~o:mulihost.0rs.org): the reader knows a sha256, asks for bytes, and hashes what comes back. The relay just needs a way to be asked by hash.

## A post as an event

We publish each post as one kind 30023 event, the long-form article kind from NIP-23. The event `content` is the exact Markdown bytes of the post, the same bytes every other host serves. The tags are:

- `d`: the slug, so the event is addressable and a newer version replaces an older one
- `title`: the post title
- `published_at`: the original publication time
- `x`: the sha256 of the content bytes, lowercase hex
- `alt`: a one-line description for clients that do not render kind 30023

The `x` tag is what makes the relay a hash-addressed store. Relays index every single-letter tag, so a query of `{"kinds":[30023],"#x":["<hex>"]}` returns the event without knowing the author or the slug. Before the publisher sends an event it hashes `content` and refuses to continue if the result differs from the `x` tag, so the two can never disagree in anything we sign.

The reader sends two filters when the link carries an author pubkey: one for kinds 30023 and 1063 with `#x` set to the hash and a limit of 5, and one for kind 30023 restricted to `authors` with the same `#x`. Without a pubkey only the first filter goes out. Whatever comes back is hashed. If the content does not hash to the hex in the link, the event is dropped. The hash in the link is the trust anchor, exactly as on every other source.

## The signature is secondary

Every event carries a Schnorr signature over its id, and the reader verifies it with a small BIP-340 implementation. We do this only after the content hash has matched. The order matters. The hash decides whether the bytes are the post; the signature only decides whether the event could have come from the key in the link. A relay cannot forge content that hashes to our hex, so a bad signature on matching content tells us something odd happened at the relay, not that the post is wrong. We reject such events anyway, because a relay that stores unsigned events is not behaving like a relay, but the signature is an attribution check, not the integrity check.

The practical consequence: a link without a pubkey still verifies fully. The `pub` part of the fragment described in [the link format post](#v1.5b9263cbfcc93c7222b1459a781f871e335adf7444e2ddf21c4e4dded1ee2de5.5cedf17233b099062a5c68724d24b0a42fe5be22c779553debd23fc3f06a42e4.g:GaussRun/inbrowser-magnets~o:mulihost.0rs.org) adds a second filter and a UI line, nothing more.

## 64 KiB of JSON

Most free relays run strfry, and strfry ships with `maxEventSize = 65536`. That is bytes of normalised event JSON, not bytes of Markdown. NIP-11 documents usually advertise `max_message_length: 131072`, which is the WebSocket frame size and says nothing about the event cap. Markdown grows when it is JSON-escaped (every newline becomes two characters, every quote gains a backslash), so the realistic budget is 55 to 60 KB of Markdown per event.

We tested this with three posts of 995, 18,468 and 98,125 bytes against ten relays:

- relay.damus.io
- nos.lol
- nostr.oxtr.dev
- relay.primal.net
- schnorr.me
- relay.illuminodes.com
- nostr.mom
- purplerelay.com
- nostr-01.yakihonne.com
- relay.nos.social

The small and the medium post were accepted by 9 of 10 relays and read back with a matching hash from all 9. The large post became a 100,657 byte event. Five relays refused it with the same text:

```text
invalid: event too large: 100657
```

Those five were nos.lol, nostr.mom, purplerelay.com, schnorr.me and nostr-01.yakihonne.com, all strfry at the default cap. The earlier read-only research had listed schnorr.me as a relay that accepted 88 KB events in a previous test, so operators do change these settings; the only reliable number is the one you measure on the day. Four relays took the event: nostr.oxtr.dev, relay.primal.net, relay.nos.social and relay.illuminodes.com. relay.illuminodes.com and relay.nos.social already stored kind 30023 events of 182,112 bytes from other authors, so their caps are far higher.

The event ids are stable across runs because we keep the signed events on disk and resend the same ones. The 98 KB post is event `32c7ebfa31184cce4c6588d4441616b59a51465bc7a1a2996aab5b20aa89ce50`, the small one is `ca0494ed5d9fc244f191ba11de5b4e7953d038b3c80542fb1fb826a170d8b0b1`, both under pubkey `5cedf17233b099062a5c68724d24b0a42fe5be22c779553debd23fc3f06a42e4`.

## relay.damus.io

The tenth relay deserves its own paragraph. relay.damus.io sits behind Cloudflare and intermittently answers the WebSocket upgrade with an HTTP 503. Node's built-in WebSocket reports that as a close with code 1006 and no further detail. The `ws` package at least surfaces the non-101 response, and connects when Cloudflare lets the upgrade through. In the final publishing run every attempt failed at the handshake, which is why the counts above say 9 of 10 for the small posts. In an earlier run the relay accepted two events and then went silent without sending `OK` for the rest. The research notes say it bans an IP that writes about one event per second and that the ban was still in place 23 minutes later. We treat it as the relay with the widest reach and the least patience.

## Pacing

Relays are the one host type where a publisher can get itself banned by being quick. Our rules, taken from the research and confirmed in the run:

1. One WebSocket per relay per run. Different relays in parallel, events on one relay strictly serial.
2. At least 3 s between events on a relay. On relay.damus.io 10 s, and at most about five events per run.
3. On an `OK false` with reason `rate-limited:` back off 30 s once, then give up on that relay for this run.
4. Publish kind 0 (profile) and kind 10002 (relay list) before any kind 30023, with one long-lived author key. A brand-new key sending large events is exactly what web-of-trust filters reject.
5. Never backdate `created_at`. Default strfry rejects events older than three years, so a refresh job has to re-sign with a fresh `created_at` and keep the original date in `published_at`.

A post costs one to three events per relay. The limits only bite when a whole blog is backfilled at once, so backfills run at about one post per relay per minute.

## The second route: kind 1063

For posts that do not fit in 64 KiB there is a smaller event that does. Kind 1063 is the NIP-94 file metadata kind. It carries `x` with the sha256, `m` with the MIME type, `size`, and one `url` tag per copy of the file, typically the Blossom servers that hold the blob under its hash. The event is a few hundred bytes and every relay accepts it.

The reader already queries kind 1063 alongside kind 30023 in the same `#x` filter. When a 1063 arrives it checks the `x` tag, verifies the signature, and fetches each `https://` URL with `integrity: sha256-<b64>`, so the bytes are still verified by the browser before anything is rendered. The relay then acts as an index that points at mirrors rather than as the store itself. It is slower than a direct Blossom hit, since it costs a WebSocket round trip and then an HTTP fetch, but it gives a post over 64 KB a presence on every relay.

## Practical advice

- Keep a post under 64 KB of Markdown if relays must carry the full text. Under 55 KB leaves room for JSON escaping on every strfry relay.
- Above that, send the full kind 30023 only to relays known to accept large events (nostr.oxtr.dev, relay.primal.net, relay.nos.social, relay.illuminodes.com in our run), and a kind 1063 pointing at Blossom to all of them.
- Expect churn. The read-only probe found 12 of 66 well-known relay names dead or broken, one of them a verified writer three weeks earlier. The reader's list is static data, and the publisher's `check` step is what keeps it true.

Relays are band 16 in the reader's race: after Blossom, Arweave by txid and Software Heritage, before the owner host. They are a good source for small posts and an index for large ones, and a poor place to store 100 KB of anything.
