# Why one https link cannot survive its host

We share links all day and think of them as addresses for a piece of writing. They are not. They are addresses for a machine. `https://alice.example/why-the-bridge-failed` says: connect to whatever answers for the name `alice.example`, ask it for that path, and show whatever comes back. The post is not in the link. The post is whatever the host chooses to return today.

This note is about why that is a problem, why the usual DNS fixes do not fix it, and what we built instead.

## What a link really names

A plain `https://` link fuses three things that have nothing to do with the content:

- a name, resolved through DNS to one or more addresses
- a server that happens to answer at those addresses and holds a certificate for the name
- a path that the server maps to some bytes, by rules only the server knows

The browser trusts the result because the certificate matches the name. It never compares the bytes with anything. If the server returns a different text, a 404 page, or a seizure banner, that is what the reader gets, with a green padlock.

Now take the host away. The domain lapses, the hosting account is closed, the registrar hands the name to someone else, a network blocks it. Copies of the post may well exist elsewhere: in an archive, on a mirror, under the author's other accounts, in a friend's clone of the repo. None of them can be reached from the link, because the link does not know they exist. The copies are fine. The link is what is broken.

## Why pointing the name at several servers does not help

The first idea everyone has, including us, is to publish several A records for the name and let the browser fail over. We measured this in Chromium 156 and Firefox 157 against a local DNS-over-HTTPS server, with addresses that refused the connection, addresses that dropped packets, addresses that answered 404, and addresses that presented a certificate for the wrong name. The next post has the full tables. The result that matters here is short.

Browsers move on to the next address only when the TCP connection fails. A refused connection is cheap in both engines. A dropped connection costs about 0.3 s in Chromium with two addresses and the full 75 s operating system timeout in default Firefox. But neither of those is what happens on a takedown.

What static platforms actually do when a site is removed, or when a domain points at them without being configured, is answer. GitHub Pages serves a certificate for `*.github.io` and an HTTP 404. Netlify serves a certificate for `*.netlify.app` and a 404. Vercel closes the TLS handshake without a certificate. Codeberg Pages sends a TLS alert. None of them refuses the connection, so none of them triggers the failover. In the lab, a first address answering 404 was shown as a 404, and a first address with a wrong-name certificate was a hard TLS error, in both engines, with no retry on the second address. On top of that, most of these platforms issue their certificates with the HTTP-01 challenge, which fails or flaps when only one of N addresses points at them, and GitHub, Vercel, GitLab and Render say so in their own docs.

HTTPS/SVCB records with a TargetName were the second idea. Chromium 156 ignores TargetName entirely. Firefox 157 follows it but, by default, does not fail over to the second target when the first one is dead.

We went through the rest of the list as well: Alt-Svc, CNAME chains, Signed HTTP Exchanges, Metalink, `rel=duplicate`. Each one either protects against a single server dying under a name that still works, never reached browsers, or is being retired. Nothing in the web platform lets one `https://` link to one domain outlive that domain for a first-time visitor.

## Name the content instead

The way out is older than the web: name the thing by what it is. The sha256 of the exact bytes of a Markdown file is 64 hex characters. Anyone who has the bytes can compute it. Anyone who receives bytes from anywhere can check them against it. The host stops being part of the trust story and becomes what it should have been all along, a place where a copy might be.

So the link carries two kinds of information, both after the `#`:

- the hash, which says exactly what the reader should get
- hints, which say where copies were last known to be

```
https://mulihost.0rs.org/#v1.312453b85dbbece038586643c5cb220e8925b8a1700d121b37f4a9acdd70fcd0.g:GaussRun/inbrowser-magnets~o:mulihost.0rs.org
```

The hints can all be wrong without the link being wrong. The GitHub repo can be deleted, the owner host can be seized, and the hash is still the hash. The reader page also knows a set of hosts that need no hint at all, because they address content by its hash: Blossom servers answer `https://<server>/<hex>`, Software Heritage answers by `sha256:<hex>`, Arweave can be searched by a `Content-SHA256` tag, IPFS gateways take a CID that is the same sha256 with four prefix bytes, and Nostr relays can be asked for events carrying the hash. Copies on those hosts are reachable from the link even though the link never mentions them.

Everything after `#` stays in the browser. The host serving the reader page sees `GET /` and nothing else, so it cannot log which post was opened and cannot be told to block one post without blocking all of them. Any copy of the reader page on any domain opens the same link.

## The race

The reader is one static HTML file with no framework and no IPFS library. It reads the fragment, expands the hints and the built-in lists into a flat list of URLs, and starts fetching. Three requests go out at once, two more are added every 300 ms, and at most eight are in flight. Each request is a plain `fetch()`. The reader hashes every response and refuses any whose bytes do not match the link. The first verified copy wins and the rest are aborted.

![The race: three Blossom servers at 0 ms, Arweave and Nostr at 300 ms, the owner host and GitHub at 600 ms; the first verified copy wins](sha256:8dafe1b323326059495fc98751b1ef64e2ce1deec57703c35b72f901dc4e49ef)

The order is not an accident. Hosts that need no signup and are addressed by the hash alone go first: Blossom, Arweave, Software Heritage, Nostr. The owner's own host and the GitHub-derived mirrors come after. IPFS gateways sit last, kept on principle. If a hint names a dead host, that host costs one failed request in a race it was never going to win alone.

A tampered copy is not a special case. A mirror that serves altered bytes fails the hash check like any other wrong answer, and the race goes on. Only hash-verified bytes are rendered, inside a sandboxed iframe with no script permission.

## What this does and does not fix

It fixes the case we care about: a first-time reader, in a normal browser, with no extension, opening a link a year later while the home host is dead, blocked or seized, and getting the exact text in under a second from whichever copy is reachable, with a verified badge.

It does not remove the need to reach one copy of the reader page. That page is the one thing a censor would go after, so it is published to places where it cannot be removed as well as to the usual free hosts: Arweave by transaction id, IPFS by CID, nsite under a Nostr key, GitHub Pages, and the owner's domain. The same single file works unchanged from any of them, and every copy shows where the others are.

And it does not keep the host alive. The host can still die. The link just stopped caring.
