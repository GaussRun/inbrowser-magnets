# What we measured about browser DNS failover

In [the first post](#v1.bd1a16da7322254332a1bf541f3024267347635aa059c56533ef7ccb56cbfff2.5cedf17233b099062a5c68724d24b0a42fe5be22c779553debd23fc3f06a42e4.g:GaussRun/inbrowser-magnets~o:mulihost.0rs.org) we said that pointing a name at several servers does not save a link from a takedown. This is the lab behind that sentence. We wanted real numbers from real browser engines, not folklore about Happy Eyeballs, so we built a fake zone, served it over DNS-over-HTTPS to Playwright-driven browsers, and timed the page load for each kind of dead first address.

## The lab

- A DNS-over-HTTPS server on `https://127.0.0.1:8053/dns-query` serving a made-up zone `*.lab.example` with A, AAAA and HTTPS (type 65) records, TTL 60.
- HTTPS web servers on port 8443, with a local test CA, a good leaf certificate for `*.lab.example`, and a deliberately wrong leaf for `*.github.io`, which is what the GitHub Pages address 185.199.108.153 presents for a host it does not know.
- Playwright 1.64.1, Chrome for Testing 156.0.8078.4 and Firefox 157.0, a fresh browser per scenario.
- macOS with `net.inet.tcp.keepinit` at 75000 ms. That is the 75 s number that shows up below whenever a browser waits for the operating system to give up on a connection.

Each address on port 8443 played one role:

- good: 127.0.0.1, ::1 and a local ULA address, valid certificate, 200 with the body `GOOD`
- refused: a LAN IPv4 and a local global IPv6 with nothing bound, so the kernel answers with an immediate RST
- blackhole: 192.0.2.1, 198.51.100.1, 2001:db8::1 and 2001:db8::2, where the SYN is dropped and nothing ever answers (we checked for 6 s)
- 404: the refused address, this time with a server bound, valid certificate, HTTP 404
- wrong cert: the same address serving the `*.github.io` leaf from our CA

Driving Chromium took some trial and error. What worked: setting DoH through the user-settable prefs in a persistent profile (`dns_over_https` with `mode` `secure` and our template), trusting the good leaf with `--ignore-certificate-errors-spki-list`, and reading connect attempts from `--log-net-log`, where every `TCP_CONNECT_ATTEMPT` is timestamped. What did not work: the field-trial flags for DoH were ignored, the netlog kept showing the system's auto-upgrade template with an empty field trial list. `--host-resolver-rules` cannot map one name to several addresses either; with two addresses in one MAP rule only the first was used, and the page failed with `ERR_CONNECTION_REFUSED` in 6 ms.

Firefox was simpler: `network.trr.mode=3`, `network.trr.uri` pointing at our server, `network.trr.confirmationNS=skip`, `network.trr.allow-rfc1918=true`, and the test CA imported into a profile template with `certutil`, so certificate validation stayed fully on. One variant added `network.http.happy_eyeballs_enabled=true`, and one rerun logged `nsHostResolver` and `nsSocketTransport` at level 5 to see what the sockets were doing.

WebKit we could not drive at all. Playwright WebKit on macOS resolves names through the system resolver, mDNSResponder, and has no DoH or host-resolver switch. The only levers are `/etc/hosts` and `/etc/resolver/*`, which need root. We also tried registering two mDNS A records for one `.local` name through two `dns-sd -P` processes; mDNSResponder rejected the second as "Name in use". So a single name with two addresses cannot be built for WebKit without root, and everything we say about Safari comes from published measurements.

## A and AAAA failover

The DNS answer kept the order we listed, with the good address second unless noted, and Chromium's netlog confirmed it tried addresses in that order in default mode. Times are from navigation start to the rendered `GOOD` page.

First address refused:

- IPv4, Chromium 156: 42 ms, the good address was tried in the same millisecond
- IPv6, Chromium 156: 72 ms, and 75 ms with HappyEyeballsV3 forced on
- IPv4, Firefox 157: 251 ms, which is the Firefox baseline in this lab, about 230 to 260 ms for anything
- IPv6, Firefox 157: 254 ms, and 261 ms with the Happy Eyeballs v3 pref

So a refused connection is free. Both engines add under 10 ms for it.

First address blackholed, two addresses in the record:

- IPv4, Chromium 156 default: 340 ms, the second address was raced at about 300 ms
- IPv6, Chromium 156 default: 332 ms, and 291 ms with HappyEyeballsV3
- IPv4, Firefox 157 default: 75273 ms, the full operating system timeout
- IPv4, Firefox 157 with the v3 pref: 310 ms
- IPv6, Firefox 157 default: failed after 455 ms with `NS_ERROR_UNKNOWN_HOST`
- IPv6, Firefox 157 with the v3 pref: 308 ms

Two blackholes before the good address:

- IPv4, Chromium 156 default: 75068 ms, the third address was tried only after the OS timeout
- IPv6, Chromium 156 default: 75092 ms
- IPv6, Chromium 156 with HappyEyeballsV3: 547 ms, one address every 250 ms
- IPv4, Firefox 157 default: 75290 ms
- IPv4 and IPv6, Firefox 157 with the v3 pref: 411 ms and 413 ms
- all addresses blackholed: Chromium `ERR_CONNECTION_TIMED_OUT` at 75023 ms, Firefox `NS_ERROR_NET_TIMEOUT` at 75213 ms

![Time to a rendered page when the first address is dead: refused versus blackholed, Chromium 156 and Firefox 157](sha256:6a767a3179cb6c41deeccd66f4fc8758b5d42c811f16ff3c74e50f42e0491e37)

Two of those rows deserve a closer look.

The Chromium default netlog for three addresses shows the first blackhole at +32 ms, the second at +337 ms, and then nothing until +75034 ms, when the good address is finally tried. Chromium races exactly one backup connection about 300 ms after the first. It is not Happy Eyeballs across the whole list. With the `HappyEyeballsV3` feature forced on it does stagger through every address 250 ms apart, but Chrome 156 does not enable that by default. It also sorts addresses by RFC 6724 in that mode, which put 127.0.0.1 ahead of 192.0.2.1 and made our IPv4 blackhole cases meaningless, so those were repeated over IPv6, where the dead 2001:db8::/32 address sorts ahead of the ULA.

The Firefox IPv6 failure was traced in the socket log. The primary socket tries 2001:db8::1. After `network.http.connection-retry-timeout`, 250 ms, a backup socket starts, and that backup resolves IPv4 only. Its A query returns no records, and that `NS_ERROR_UNKNOWN_HOST` ends the page load. A dual-stack name with a working A record never hits this, but an IPv6-only name whose first AAAA is dead fails outright in default Firefox 157, in under half a second, without ever trying the second AAAA.

On the Happy Eyeballs v3 state: Mozilla bug 2062892, "Enable Happy Eyeballs v3 by default", is resolved fixed for desktop with milestone 155, and a comment there says it was disabled again for 155 and 156 after proxy breakage. The Playwright Firefox 157 build behaved as if it were off. We did not verify the release channel.

## The cases that actually happen

Blackholes and refused connections are what you get when a machine is unplugged. They are not what you get when a platform removes a site. For that we tested a first address that answers.

- first address answers 404: Chromium shows the 404 after 82 ms, Firefox after 285 ms. No failover in either.
- first address serves a wrong-name certificate: Chromium `ERR_CERT_AUTHORITY_INVALID` after 257 ms with an interstitial, Firefox `SSL_ERROR_BAD_CERT_DOMAIN` after 193 ms. No failover in either.

Chromium reports authority invalid rather than name mismatch only because our lab CA is trusted through the SPKI allowlist of the good leaf. The netlog shows `SSL_CONNECT` failing and no further `TCP_CONNECT_ATTEMPT`. Firefox, with the CA properly trusted, gives the exact GitHub-style case: a bad certificate domain, and the load stops there.

We then checked what free static platforms send for an unknown or removed host, with `openssl s_client` and `curl --resolve` against their published apex addresses. GitHub Pages: certificate for `*.github.io`, HTTP 404. Netlify: `*.netlify.app`, 404. Surge: `*.surge.sh`, 404. GitLab Pages: `*.gitlab.io`, 302. Vercel: the TLS handshake is closed with an unexpected EOF, no certificate. Codeberg Pages: TLS alert 80. Render: a Cloudflare edge certificate and HTTP 530. Every one of them accepts the TCP connection. Not one of them produces the only signal a browser fails over on.

## HTTPS and SVCB records

RFC 9460 lets an HTTPS record carry a TargetName and a priority, which on paper is exactly a failover list. We served records at `_8443._https.<name>`, which both browsers queried.

- an origin with only an HTTPS record pointing at a good target: Chromium 156 `ERR_NAME_NOT_RESOLVED`, it never queried the target; Firefox 157 rendered in 229 ms
- priority 1 refused, priority 2 good: Chromium `ERR_NAME_NOT_RESOLVED`; Firefox default `NS_ERROR_UNKNOWN_HOST` after 196 ms, it tried priority 1, then fell back to the origin's own A record, which did not exist, and never tried priority 2; Firefox with the v3 pref passed in 251 ms
- priority 1 blackholed, priority 2 good: Chromium `ERR_NAME_NOT_RESOLVED`; Firefox default `NS_ERROR_UNKNOWN_HOST` after 75200 ms; Firefox with the v3 pref 280 ms
- `ipv4hint` with a refused and a good address, no A record: Chromium `ERR_NAME_NOT_RESOLVED`; Firefox 245 ms, it used the hints and failed over within them
- an HTTPS record with target `.` plus a plain A record set of refused and good: Chromium 45 ms, Firefox 225 ms, which is just the ordinary A failover

Chromium ignores TargetName and the hints completely. That matches the published client matrix from DNS-OARC 44, where Chrome and Edge use only `alpn`, Safari supports AliasMode, ServiceMode TargetName, port and hints, and Firefox supports ServiceMode TargetName, port and hints but not AliasMode. An open Chromium issue still lists "following target names in ServiceMode records, to handle multi-CDN use cases" as missing. Firefox's own unit test for TRR HTTPS fallback expects fallback across records, and notes that without an `echconfig` the client goes straight to the origin, which is exactly the default-mode failure we saw.

Sources: https://bugzilla.mozilla.org/show_bug.cgi?id=2062892, https://searchfox.org/firefox-main/source/netwerk/test/unit/test_trr_https_fallback.js, https://indico.dns-oarc.net/event/52/contributions/1156/attachments/1092/2234/OARC44_%20DNSHTTPSStudy.pdf, https://blog.apnic.net/2025/10/07/analysing-the-state-of-happy-eyeballs-implementations/

## What we took from it

1. Multi-A failover protects against one thing: an address that stops answering TCP. A refused connection is free. A blackhole costs about 0.3 s in Chromium with two addresses, up to 75 s in default Firefox, and up to 75 s in Chromium as soon as two addresses are dead.
2. A takedown never looks like a dead address. It looks like a 404, a wrong-name certificate or a TLS alert after a successful connect, and all of those end the page load in both engines.
3. Adding records across platforms costs certificate validity, because HTTP-01 validators resolve the name themselves and may land on the wrong platform.
4. HTTPS record TargetName failover is not usable today: Chromium ignores it and default Firefox does not fail over between targets.
5. A browser may cache the whole record set for the TTL, so a dead address listed first costs every visitor that delay until the record changes, and changing it means something has to run after publishing, which we ruled out.

So the failover lives in the application layer. The reader page tries many hosts itself, in parallel, verifies every answer by hash, and does not care what the first one returned. That is the only layer where a 404 and a dropped packet are the same thing: one loser in a race.
