# Arweave free tier limits

Blossom servers and Nostr relays are run by volunteers who promise nothing about retention. Arweave is the opposite: you pay once and the network is designed to keep the data. For small files the price is zero, which is what makes it a core host rather than an optional one.

## The free tier, in numbers

Turbo is the upload service run by ArDrive on top of the ar.io network. Its `https://upload.ardrive.io/info` endpoint states the free tier directly:

- `maxItemBytes`: 107,520 bytes per data item (105 KiB)
- `lifetimeBytes`: 10,485,760 bytes (10 MiB) per wallet
- `ipBytes`: 10,485,760 bytes per IP, counted per /24 subnet according to the docs

Both caps must have room. When one is exhausted the upload answers HTTP 402 with `FREE_TIER_EXHAUSTED`. A fresh address can check its allowance at `https://payment.ardrive.io/v1/account/free?address=<addr>`; a new one returns `bytesRemaining: 10485760`. Rotating keys resets the wallet cap but not the IP cap.

The per-item limit is why every post in this blog is kept under 107,520 bytes. It is the tightest limit among the core hosts and it is a hard one, so it became the publisher's rule for posts. Ten MiB of text is about a thousand posts of 10 KB, which is more than this blog will see; images over the limit cost money at $77.96 per GiB, so a 300 KB image is about two cents.

## The unsigned route answered 402

Turbo offers an unsigned upload (`uploadRawX402Data` on an unauthenticated client) that needs no key at all. We tried it first, since a publisher with no key material is the simplest publisher. Every file, including the 995 byte post, came back with HTTP 402 and an x402 payment quote:

```json
{
  "x402Version": 1,
  "accepts": [{
    "scheme": "exact",
    "network": "base",
    "maxAmountRequired": "21488",
    "resource": "https://upload.ardrive.io/v1/tx",
    "description": "Upload 2803 bytes to Arweave via AR.IO Bundler",
    "mimeType": "text/markdown",
    "payTo": "0x6A0A10FFD285c971B841bee8892878c0d583Bf67",
    "maxTimeoutSeconds": 3600,
    "asset": "0x833589fCD6eDb6E08f4c7C32D4f71b54bdA02913",
    "extra": { "name": "USD Coin", "version": "2" }
  }],
  "error": "Payment required to upload data"
}
```

The quote asks for USDC on Base. The 2803 bytes in the description is the signed data item, not the 995 byte post; the signature, owner and tags add about 1.8 KB. Whether the x402 route is meant to have a free tier at all is not stated anywhere we found, so we stopped guessing.

## Signing with a throwaway key

The signed route is the one the free tier documents. Turbo accepts Arweave JWK, Ethereum and Solana signers. We generated a 32 byte Ethereum private key with no funds and no history, kept it in the publisher's environment, and used `TurboFactory.authenticated` with it. All four files were accepted with `winc 0`, meaning zero Winston Credits charged. The owner address derived from the key is `Tt9abPib3F5rC2i_yo7spdeXj2wZW3gHQNuPgFcJhxg`, and it is the same for every re-run because the key is reused.

The posts received these transaction ids:

- hello-magnets (995 bytes): `JpCbBtEL62oENawwQnAT5r-bw7jETYeP55s2KLqGacA`
- medium-post (18,468 bytes): `Blj4iEBiBZMrcVjWC75n2j_FmMCu2n408dZSxeLRKD8`
- large-post (98,125 bytes): `6ItnT2Xn4-BrG5OZv702Z-sE2rmAligSW35ifBko-p8`

Signing with our own key has a second benefit. The data item's `owner` proves who uploaded it, so a lookup can filter on the owner address and ignore anything else carrying the same tags.

## Tags

A data item carries arbitrary name and value tags. Ours are:

- `Content-Type`: `text/markdown` for posts, `image/png` for the test image
- `Content-SHA256`: the lowercase hex sha256 of the bytes
- `App-Name`: `inbrowser-magnets`
- `File-Name`: `<hex>.md` or `<hex>.png`

`Content-SHA256` is the one that matters. It makes the post findable by the same hash that is in the link, through GraphQL, without a transaction id.

## Four gateways serving raw bytes

Arweave gateways serve a transaction's bytes at `/raw/<txid>`. The reader's list is arweave.net, ar-io.dev, turbo-gateway.com and ardrive.net. Every one of them returned all four files with the right byte count, a matching sha256 and `access-control-allow-origin: *`. The plain `/<txid>` path on arweave.net answers with a 302 to a sandbox subdomain, which is fine for a browser navigation and useless for a cross-origin fetch whose bytes must be checked, so the reader always uses `/raw/`.

ar.io gateways also send an `x-ar-io-digest` header, the base64url sha256 of the body. It is a cheap pre-check and nothing more; the reader hashes the body itself regardless. The gateway registry at `https://ardrive.net/ar-io/peers` listed 330 gateways at probe time, so the four in the list are a starting point, not the ceiling.

Latency: turbo-gateway.com serves a fresh item immediately from its optimistic cache. One observed item was in an L1 block about three minutes after its upload timestamp, after which any gateway can serve it. One caveat on the word permanent: gateways honour content moderation blocklists, so a single gateway can decline to serve a transaction that is firmly on the weave. That is another argument for listing several.

## Two ways into the race

The transaction id is not derivable from the hash, so the reader has two paths.

With an `a:<txid>` hint in the link (see [the link format post](#v1.5b9263cbfcc93c7222b1459a781f871e335adf7444e2ddf21c4e4dded1ee2de5.5cedf17233b099062a5c68724d24b0a42fe5be22c779553debd23fc3f06a42e4.g:GaussRun/inbrowser-magnets~o:mulihost.0rs.org)) the reader expands it to `https://<gw>/raw/<txid>` for each of the four gateways. These sit in band 12, right behind the Blossom servers from [the Blossom post](#v1.b1ab521491a8fd506c27dd599d41862604873e761eed31525d9f6a0b7e7dbb16.5cedf17233b099062a5c68724d24b0a42fe5be22c779553debd23fc3f06a42e4.g:GaussRun/inbrowser-magnets~o:mulihost.0rs.org), so they are in the first second of the race.

Without the hint, the reader falls back to GraphQL:

```graphql
query {
  transactions(first: 10, sort: HEIGHT_DESC,
    tags: [{ name: "Content-SHA256", values: ["<hex>"] }]) {
    edges { node { id tags { name value } block { height } bundledIn { id } } }
  }
}
```

sent to `https://arweave.net/graphql` and `https://ardrive.net/graphql`, both with CORS `*`. The result gives the txid, and the reader then fetches `/raw/<txid>` and hashes the bytes like any other URL. This is band 60, the last band, because it is two round trips and the indexes are uneven: in our run `ardrive.net/graphql` found all four items, while `arweave.net/graphql` found the first and answered the other three with an HTML error page instead of JSON. The lookup still works, it is just slow and occasionally flaky, which is exactly what the last band is for. Spoofed items with our tag are harmless: the bytes are hashed before anything is shown.

Every link this blog hands out carries the `a:` hint, so the GraphQL path is only for links that were written by hand or that lost their hints.

## Why permanence matters for the design

The reader is built around the idea that a link should keep working after the author stops paying attention. The home host can lapse, a Blossom operator can wipe a disk, a relay can prune old events. Those hosts are fast and free, and they are where a post is read from on an ordinary day. Arweave is the host that is still there on a bad day years later, because the storage was paid for at upload, by the network's endowment rather than by a monthly bill nobody is paying any more.

For that to be true the post has to fit under 107,520 bytes and the publisher has to keep the signing key and the txids. We write the txid into every link and into the manifest, and the `Content-SHA256` tag means that even a reader with only the hash can still get there.
